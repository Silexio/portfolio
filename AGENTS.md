# Portfolio Silexio

Site bilingue (FR défaut + EN) de Silexio, studio d'ingénierie indépendant — silexio.be. Une landing one-page (`/fr`, `/en`) et trois pages dédiées à slug localisé (`/fr/automatisation`, `/fr/logiciel-metier`, `/fr/depannage` et leurs équivalents anglais), toutes 100% statiques (SSG). La réservation (cf. § Réservation) et le formulaire de demande (cf. § Formulaire) introduisent le seul code serveur dynamique du projet (Route Handlers serverless) — les pages restent SSG.

## Commandes

```bash
pnpm dev              # dev server (les bindings wrangler sont injectés par initOpenNextCloudflareForDev)
pnpm build            # build prod — /fr, /en, /[lang]/legal et les 6 pages dédiées doivent rester ● (SSG) ; /api/* et /[lang]/booking/[action] sont ƒ (dynamiques, attendus)
pnpm lint             # eslint, zéro warning toléré
pnpm test             # vitest — lib/**/*.test.ts uniquement (unit)
pnpm test:e2e         # playwright — e2e/*.spec.ts (chromium + mobile iPhone 13), démarre le dev server. `npx playwright install` une fois.
pnpm preview          # build OpenNext + exécution locale dans workerd — le vrai runtime de prod
pnpm deploy           # build OpenNext + déploiement Cloudflare
pnpm db:migrate       # applique migrations/ à la D1 locale (.wrangler/state)
pnpm db:migrate:remote# idem sur la D1 de prod
pnpm cf-typegen       # régénère cloudflare-env.d.ts (auto en postinstall) — relancer après toute modif de wrangler.jsonc
```

**`pnpm smoke`** construit la sortie OpenNext, la sert dans **workerd** et relit ce que le Worker renvoie : **les pages listées par le sitemap du site lui-même** — une page ajoutée est couverte sans qu'on y pense —, `/robots.txt`, `/sitemap.xml`, `/api/availability`, la présence d'un `<h1>`, l'absence de `siteKey:""` dans le HTML servi, et l'absence de `NoFallbackError` ou de `WebAssembly.compile` dans le journal du runtime. Il tourne aussi en CI.

**Pourquoi il existe** : le 2026-10-10, `pnpm lint`, `pnpm test` et `pnpm build` étaient tous verts pendant que **le site entier répondait 404 en production**. Ces trois commandes vérifient le code et la sortie de Next, jamais ce que le Worker sert vraiment. La cause était une incompatibilité entre Next 16.3.8 et `@opennextjs/cloudflare` 1.20.2 : les pages prérendues n'étaient plus servies, chaque route du segment `[lang]` tombait sur `NoFallbackError`, et rien dans la chaîne de vérification ne pouvait le voir avant la mise en ligne. **Ne jamais retirer ce contrôle pour accélérer le CI** : il est le seul à exercer le runtime de production.

`pnpm start` n'existe plus : la prod tourne sur workerd, pas sur le serveur Node de Next. Pour tester le comportement réel, c'est `pnpm preview`.

## Architecture

- `app/[lang]/` — seul segment de routes. `generateStaticParams` + `dynamicParams = false`, y compris sur `app/[lang]/[service]` (pages dédiées), dont le `generateStaticParams` reçoit la langue du parent de façon **synchrone** (`{ params: { lang } }`). Les params de page Next 16 sont des Promises : toujours `localeParam(params)` (lib/i18n/utils.ts), jamais de cast.
- `/` → redirect 308 vers `/fr` (next.config.ts), `x-default` hreflang pointe sur `/fr`.
- `lib/data.ts` — TOUT le contenu UI vit ici en `Bilingual { fr, en }`. Jamais de string utilisateur en dur dans un composant.
- **Positionnement** (refonte du 2026-09-21, spec : `docs/superpowers/specs/2026-09-21-repositionnement-silexio-design.md`) : le site vend un **résultat** (« la tâche que vous refaites chaque semaine peut disparaître »), pas une compétence technique. Cible : PME wallonnes de 5 à 50 personnes. Le dépannage IT des particuliers est **sorti de la landing** vers `/[lang]/depannage` : il rapporte vite mais tirait la marque vers « informaticien local ». Toute réécriture de contenu doit tenir cette ligne.
- **Charte « La pierre et le signal »** (2026-10-09, référence complète : `docs/charte-pierre-et-signal.md`, canevas <https://claude.ai/artifact/A5LUBEqGwVxJisSUwQPQsf>) : le site n'a pas de couleur. Pierre chaude le jour (`#efebe7`), graphite chaud la nuit (`#181512`), et **une seule chose s'allume, l'étincelle `--spark` (`#ffb020`)**. Les aplats d'action sont en encre, pas en couleur. Deux polices conservées (Montserrat pour les titres et le wordmark, Luciole — dessinée pour les lecteurs malvoyants et dyslexiques — pour tout le reste), surfaces taillées en facette, illustrations maison. Toute nouvelle page reprend ces primitives plutôt que d'inventer son style.
- **Pourquoi pas une couleur de marque** : mesuré le 2026-10-09, la bande orange est saturée entre 28° et 65° de teinte OKLCH par neuf marques mondiales (Anthropic 38,8°, Firefox 45,2°, Hermès 46,5°, Amazon 64,6°…) ; cinq oranges candidats tombaient tous à moins de 3° de l'une d'elles. On ne peut pas y être distinctif, c'est arithmétique. La signature est donc une **règle**, pas une teinte — comme le blanc d'Apple. Deux pièges à ne jamais rouvrir : **crème + terre cuite** (l'identité d'un éditeur d'IA, le reproche initial) et **bleu-gris** (le défaut de tous les studios de dev, pansement retiré le jour même).
- **La règle de l'étincelle** : `--spark` ne porte **jamais** de texte (1,54:1 sur la pierre claire), ne sert **jamais** d'aplat, et ne peut **jamais** porter seule une frontière de composant. Elle n'apparaît qu'à deux endroits, soit ~1 % de la surface : les 3 px du flanc frappé du bouton principal, et le balayage de la marque. Un liseré décoratif de 3 px sur un plateau clair reste admis — il ne porte aucune information et la frontière du bouton est déjà assurée par le plateau.
- **La chorégraphie de l'accroche** : les éclats jaillissent de la pierre (`flake-strike`), les libellés se posent (`chore-settle`), les traînées relient (`chore-fade`), l'étincelle part (`spark-strike`), et la marque crache sa braise (`mark-glint`). Chaque élément porte son rang `--i`, posé par `ChoreMap` comme `OfferLadder` pose `--count`. **Transform et opacity seulement**, zéro JavaScript ajouté, le tout déclaré _dans_ `@media (prefers-reduced-motion: no-preference)`. Au survol, le bouton se soulève d'un pixel et son flanc frappé passe de 3 à 6 px (`--spark-edge`).
- **Illustrations taillées** : `OfferGlyph` n'est plus un contour mais un **volume** — chaque pierre est un jeu de faces pleines, de `--stone-1` (face éclairée, en haut à gauche) à `--stone-4` (face dans l'ombre), plus une silhouette et les ondes de percussion. Les éclats de `ChoreMap` et les objets des planches `DomainArt` prennent la même lumière par un dégradé local. La progression des cinq pictogrammes raconte la taille : rognon brut, rognon entamé, éclat détaché, outil fini, outil entretenu.
- **Un serveur de peinture ne traverse pas les frontières de `<svg>`** — ni un `clipPath`. Un dégradé ou un clip déclaré dans le sprite et référencé depuis un autre `<svg>` ne s'applique pas, **sans la moindre erreur** : les éclats de l'accroche avaient disparu et le balayage de la marque ne s'est jamais peint depuis son écriture. Chaque dégradé vit donc dans le `<svg>` qui l'utilise, avec un identifiant portant sa portée (`chore-${variant}-${tone}`, `art-lit-${id}`, `silexio-glint-${scope}`) puisque les composants sont rendus plusieurs fois. Et **un `<g>` n'est pas un enfant valide de `<clipPath>`** : il est ignoré, le clip devient vide et efface tout ce qu'il devait découper — d'où la silhouette de la marque redite en deux tracés portant la matrice du sprite aplatie (`MARK_TRANSFORM`). Contrôle : capturer la zone image par image et comparer le poids des PNG ; une animation dont la transformation évolue mais dont les pixels ne bougent pas n'est pas peinte.
- **La marque est faite de trois volumes, pas de quinze fragments** (`PARTS` dans `Mark.tsx`) : lame gauche, lame droite intérieure, lame droite extérieure. Les plans d'ombre appartiennent à leur volume et ne s'en détachent **jamais** — une facette qui part seule désolidarise l'ombre de la matière, et ça se voit immédiatement. Toute animation de la marque porte sur `.knap__part`, jamais sur les tracés.
- **La pierre se forme** (`knap-form`) : dans l'accroche, les trois volumes arrivent détachés et convergent à leur place, décalés par `--i`. **Chaque volume suit son propre axe et ne change pas de taille** : le script d'amorçage lit son `getBBox()`, en déduit le vecteur depuis le centre de la marque (`MARK_CENTER`, exporté par `Mark.tsx` et passé en paramètre à la fonction sérialisée — jamais deux nombres en dur) et pose `--dx`, `--dy`, `--rot` ; l'animation n'interpole que `translate` et `rotate`. Une première version utilisait un `scale(1.5)` depuis une origine commune : les pièces **grossissaient de moitié**, débordaient de leur cadre et passaient par-dessus la note Google. Un éclat se détache, il ne gonfle pas. Les propriétés CSS `translate`/`rotate` écrasent l'attribut `transform` d'un élément SVG : la matrice du sprite est donc portée par un `<g>` parent, jamais par les tracés. **Et `transform` lui-même, même posé par une animation terminée en `both`, écrase l'attribut.** L'éclat des planches « Automatiser » et « Dépanner » portait `transform="translate(…)"` en attribut pendant que `art-fly` finissait sur `transform: translateX(0)` : sur l'accueil — la seule route où ces planches vivent dans un `[data-reveal]` — l'éclat sautait à l'origine du `viewBox`, tronqué en haut à gauche. Il était ainsi **en production**. Corrigé le 2026-10-11 en portant la translation sur un `<g>` parent, comme la lettre. Contrôle : marges gauche et droite de `getBBox()` par rapport au `viewBox`, qui doivent être égales — 67/67 pour « Automatiser », 45/45 pour « Dépanner ».
- **Physique de la pierre** (`stonePhysics`, `lib/boot.ts`) : les trois volumes s'écartent du curseur qui approche et reviennent par un **ressort intégré image par image** (k 130, c 13, amortissement 0,57), avec une impulsion au `pointerdown`. Le module ne s'attache qu'aux **pointeurs fins**, hors `prefers-reduced-motion`, et après `requestIdleCallback` : un téléphone et un visiteur qui demande moins de mouvement ne paient rien. Dès qu'il prend la main il pose `data-physics` sur la pierre, retire les animations CSS des volumes et devient seul maître de `translate` — **une animation CSS terminée et remplie l'emporterait sinon sur le style en ligne**, et les deux mécanismes se neutraliseraient en silence. La version CSS (entrée + retaille au clic) reste la base et suffit sans JavaScript.
- **Chaque visuel anime ce que l'outil fait, et rien d'autre.** Automatiser : la lettre s'envole vers le tableur puis la suivante arrive (`letter-send`), et les cellules se remplissent une à une (`art-fill`) — même cycle de 5,4 s, pour qu'on lise la cause et l'effet. Le groupe de la lettre porte déjà un `transform` d'attribut : l'animation vit sur un groupe **intérieur**, sinon les propriétés CSS `translate`/`rotate` l'écraseraient et la lettre sauterait à l'origine. Connecter : une impulsion remonte chaque liaison vers la marque (`art-signal`). Construire : la semaine se remplit de gauche à droite puis la liste du jour se coche (`art-slot`, `art-tick`). Accroche : les pointillés remontent vers la pierre (`chore-flow`). Toutes sont décalées par `--i`.
- **Les démonstrations bouclent, mais seulement sous les yeux de quelqu'un.** Ces animations sont en `infinite` et **mises en pause hors écran** (`animation-play-state: paused`, levé par `data-visible` que pose le second observateur du script d'amorçage). Elles sont rattachées à `.domain-art` et `.chore-map`, **pas à un ancêtre `[data-reveal]`** : sur une page dédiée l'illustration vit dans le hero, et les planches y restaient figées. C'est un choix du client, demandé explicitement : une planche qui se fige après trois passages se lit comme une page morte. Le prix est connu et assumé : une boucle automatique de plus de 5 secondes relève de WCAG 2.2.2 (Pause, Stop, Hide), qu'on ne satisfait pas par un bouton de pause mais par l'arrêt complet sous `prefers-reduced-motion`, par l'arrêt hors écran, et par le fait que ces planches sont décoratives (`aria-hidden`) et ne portent aucune information. **Ne pas retirer la pause hors écran** : c'est elle qui empêche cinq animations de tourner en permanence sur toute la page. Le raccourci `animation` réinitialise `animation-play-state` : la pause doit être déclarée dans la même règle que l'animation, et la règle qui la lève doit être plus spécifique.
- **Sur un écran tactile, la pierre flotte toute seule** (`knap-drift`, sous `@media (pointer: coarse)`) : la physique au curseur ne s'y attache jamais, la marque y resterait figée. Deux pixels et un demi-degré, chaque volume déphasé par son rang, déclarée **après** l'entrée dans la même liste `animation` pour en reprendre la main une fois celle-ci terminée, et mise en pause hors écran comme les démonstrations.
- **Rien de décoratif ne se sélectionne.** Libellés d'illustration, maquette de planning, pictogrammes, étoiles de la note et libellés de contrôle portent `user-select: none` ; la sélection reste à la prose.
- **Deux registres de mouvement, à ne pas mélanger.** Les **interactions** — bouton, pastille, lien, trait de navigation, marqueur de FAQ — utilisent `--ease-spring` : une `linear()` échantillonnée depuis l'équation d'un oscillateur amorti, donc de la vraie physique sans une ligne de JavaScript. Les **entrées de bloc** restent en `--ease-out` : une page dont tout rebondit fatigue. Un `--ease-bounce` et un `--dur-bounce` avaient été ajoutés « pour plus tard » : rien ne les lisait, ils ont été retirés — un jeton que la documentation annonce et que le code ignore est pire que pas de jeton. L'appui se fait en `--dur-tap` avec une sortie douce — on se soulève avec élan, on s'enfonce sec.
- **Coût mesuré du mouvement** : le script d'amorçage complet (thème, reveals, vecteurs, physique) fait **3 491 octets bruts / 1 409 gzip** en production — il était à 4 982 / 1 640 quand il s'écrivait à la main en chaînes de caractères, le minificateur du bundler le compresse mieux que nous, et la première visite de `/fr` passe de 282 à 289 Ko gzip. Motion pèse ~74 Ko transférés. Une bibliothèque d'animation ne se justifie que pour un geste que le navigateur ne sait pas produire seul.
- **Une animation terminée ne redémarre que si son `animation-name` change.** Modifier sa durée ou son délai met seulement à jour sa temporisation — elle reste terminée. D'où `knap-reform`, identique à `knap-form` sous un autre nom, pour la retaille au clic. Le symptôme est trompeur : l'attribut est bien posé, le sélecteur matche, et il ne se passe rien.
- **Animer les facettes une par une impose de rendre la marque en clair** (`<MarkFacets />`), pas par `<use>` : le CSS n'entre pas dans l'arbre fantôme. Le tracé reste écrit une seule fois, dans le tableau `FACETS` de `Mark.tsx`, dont `MarkSprite` et `MarkFacets` dérivent tous les deux.
- **Les arêtes** : `--arris-light` / `--arris-dark`, lumière fixe en haut à gauche (convention du dessin archéologique). Une facette se soulève (`inset 1px 1px 0 light, inset -1px -1px 0 dark`), une gorge se creuse (l'inverse) : un bouton se soulève, un champ se creuse. **1 px, jamais flouté** — la moindre ombre douce fait basculer dans le neumorphisme. Et **l'arête se mérite** : seulement sur l'interactif et le surélevé, sinon tout brille et plus rien ne ressort.
- **Réalisations** (`Work.tsx`) : tous les `PROJECTS` dans un **diaporama** (`components/ui/Carousel.tsx`, client) — une diapositive par projet, capture dans un cadre sombre (`frame`) ou couverture typographique au nom du projet quand la capture manque, puis nom, chips `kind`/`status`, résumé d'une ligne, technos et liens `site`/`install`/`repo` (un champ vide masque son lien). `roi` est facultatif sur un projet : tant que le client n'a pas donné ses trois chiffres (minutes avant, minutes après, rapports par semaine), la ligne « temps rendu » calculée par `lib/roi.ts` ne s'affiche pas — jamais d'estimation. La diapositive centrale est pleine, ses voisines s'estompent via une animation pilotée par le défilement (`animation-timeline: view()`), sans JS.
- L'étude de cas détaillée (`CaseStudy.tsx`), « Pour les curieux » (`Curious.tsx`) et la bande d'avis (`Proof.tsx`) ont été **supprimées** avec la charte A3 : elles pesaient deux écrans pour un patron de PME, et la note Google a rejoint l'accroche. `CASE_STUDY`, `STACK_GROUPS` et `TESTIMONIALS` ont disparu de `lib/data.ts` avec elles.
- **Avis** : la note publique s'affiche sous les CTA de l'accroche (`Rating` dans `Hero.tsx`) — étoiles remplies au prorata, texte « 5,0 · 6 avis Google », date du relevé dans le nom accessible. Seul ce qui est vérifiable chez un tiers y figure : aucun engagement que le studio se donne à lui-même (« réponse sous 24 h » est dit dans l'offre et le formulaire, pas à côté des étoiles). `REVIEWS` (Google, Trustpilot) est relevé **à la main** — `checkedOn` date le relevé. Trustpilot répond 403 à un script. Google, lui, **se relève** : un Chromium piloté avec les cookies de consentement `SOCS` et `CONSENT` posés sur `.google.com` ouvre `https://g.page/r/…` sans mur, et le panneau donne « 5,0 (6) ». Relevé du 2026-10-09 : **5,0 sur 6 avis**, catégorie « Développeur de logiciels », horaires « Ferme à 17:00 » — cohérents avec `BOOKING`. Refaire le relevé de la même façon plutôt que de recopier un chiffre de mémoire. En dessous de `MIN_REVIEWS`, la plateforme reste masquée : « 1 avis » dessert plus qu'il ne prouve. Ces notes ne vont **jamais** dans le JSON-LD : Google refuse le markup `aggregateRating` bâti sur des avis collectés ailleurs.
- **Marque Silexio** : `components/ui/Mark.tsx` — vecteur **inline**, pas une image. Le tracé (16 facettes, extrait de `public/icon.svg`) n'est écrit qu'une fois dans `<MarkSprite />`, rendu par le layout ; les usages (illustration de l'accroche, hub « Connecter », nav, footer) sont des `<use href="#silexio-mark">`. Les quatre tons du tracé viennent des jetons `--mark-1` à `--mark-4` : les instances héritent des variables de leur contexte, donc le thème sombre recolore la marque partout **sans filtre CSS ni règle par composant**. Deux raisons, mesurées : un `<img>` décoratif de 234 px était le **plus grand élément peint du hero, donc l'élément LCP**, pour une texture à 7 % d'opacité — les `<path>` SVG, eux, ne sont pas candidats au LCP ; et un tracé dupliqué serait inliné deux fois par usage dans le document (Next y embarque aussi la charge RSC). Les sélecteurs CSS ciblent `svg`, pas `img`.
- Icônes : `app/favicon.ico` doit rester en **16/32/48** (~4 Ko). Il contenait 6 tailles jusqu'à 256×256 non compressées, soit **110 Ko chargés en priorité `High`** dans la fenêtre critique — plus lourd que n'importe quelle police. `icon.png` en 192 px et `apple-icon.png` en 180 px suffisent : le manifeste porte son propre jeu `public/icon_x*.png` pour la PWA.
- `images: { unoptimized: true }` (next.config.ts) : sur Workers, `/_next/image` dépend de Cloudflare Images, non provisionné — il renvoyait l'original en payant une requête Worker de plus. Les visuels sont donc pré-dimensionnés en WebP. Toute image ajoutée doit l'être aussi.
- **Paiement** : avec Smart, le client **ne paie rien à la commande** — le devis fixe le montant par écrit, la facture part après la prestation (le devis type porte « Avance perçue : 0,00 € », le contrat « salaire net versé 7 jours ouvrables après le dernier jour de prestation »). Ne jamais réintroduire d'acompte ni d'échéancier à la signature : c'est factuellement faux pour ce statut.
- **Prix et TVA** : le montant **mis en avant est hors TVA** (décision du client, 2026-10-11), et le total TVA comprise l'accompagne (« soit X € TVA comprise »). C'est la convention de toute offre B2B, et ces tarifs s'adressent à des professionnels qui récupèrent la TVA. **La règle à ne pas perdre de vue** : l'obligation d'afficher le prix total à payer, TVA et taxes comprises, vise le prix montré **à un consommateur** (SPF Économie, directive 98/6/CE). Trois choses la tiennent, et aucune ne doit sauter : le total TTC est affiché sous chaque montant, la note sous l'échelle dit que les tarifs visent des professionnels et qu'un particulier ajoute 21 %, et la page dépannage — la seule qui s'adresse d'abord à des particuliers — **n'affiche aucun prix**. Le jour où un prix s'adresse à des consommateurs, c'est le TTC qui repasse en avant. Les montants stockés dans `OFFERS` sont hors TVA, comme le JSON-LD (`valueAddedTaxIncluded: false`), et `priceParts` (`lib/price.ts`, `VAT_RATE`) dérive l'affichage.
- **Offres et tarifs** : `OFFERS` (`lib/data.ts`) est l'échelle que gravit un client — premier échange (gratuit), audit (dès 600 € HTVA), site internet (dès 900 €), automatisation (dès 900 €), logiciel métier (dès 5 000 €), suivi (dès 99 €/mois). **Ces planchers viennent du Notion du client**, pas d'une invention : catalogue « Offres & tarifs » (la page la plus détaillée, titrée « catalogue interne ») réconcilié avec le « Business Plan » quand les deux se recoupent. Les deux pages Notion **se contredisent** sur le récurrent (99/199/249/499 contre 79/149/249) et sur le logiciel métier (le catalogue descend à 2 500 €, le BP part à 5 000) : le site retient à chaque fois la lecture la plus défendable devant un client, et c'est au client de trancher s'il veut bouger. L'échelle précédente (490 / 1 500 / 4 500 / 150 €) **ne venait d'aucune source** — elle avait été posée pendant la refonte. C'est **le seul endroit où vivent les prix** : `OfferLadder` les affiche via `priceParts` (pur et testé), le JSON-LD en dérive, la FAQ y renvoie sans les recopier. Chaque offre porte un **pictogramme** (`components/art/OfferGlyph.tsx`) : un stade de la taille du silex — rognon brut, rognon mesuré, lame, éclat détaché, outil emmanché, outil entretenu. Sous 900px l'échelle est une liste de lignes ; au-delà, une colonne par offre (`--count`) et **cinq lignes de sous-grille** partagées (pictogramme, nom, prix, hors-TVA, résumé) : le `span` et `grid-template-rows` doivent compter pareil, sinon les deux derniers textes se superposent.

- **Solutions** (`Solutions.tsx`) : `DOMAINS` = Automatiser / Connecter / Construire. Chaque panneau tient en un verbe, une promesse d'une ligne, un lien « En savoir plus » vers sa page dédiée et **une illustration** (`components/art/DomainArt.tsx`) : PDF qui se recopient dans un tableur, logiciels reliés autour de la marque, planning d'équipe. Les exemples en liste ont quitté l'accueil — ils vivent dans les situations des pages dédiées. Un renvoi discret vers le dépannage ferme la section. L'ancien panier de packages (`usePackages`, `PackageCard`, `ContactActions`) a été supprimé avec la refonte de septembre.
- **Illustrations** (`components/art/`) : **une planche par fichier** (`AutomateArt`, `ConnectArt`, `BuildArt`, `RepairArt`, `WebsiteArt`), `DomainArt.tsx` ne garde que la table d'aiguillage, et `shared.tsx` porte les deux primitives réellement partagées (`ArtLight`, `FLAKE`). Elles tenaient dans un seul fichier de 477 lignes où il fallait défiler pour trouver un composant. Contrôle de la découpe : comparer le SVG rendu avant et après dans `.next/server/app/fr.html` — il doit être identique à l'octet près. SVG serveur, `aria-hidden`, zéro couleur en dur — chaque teinte est un jeton, donc le thème sombre est gratuit. Leurs libellés (corvées autour de la pierre, noms de logiciels, planning d'exemple) vivent dans `ART` (`lib/data.ts`) et se traduisent comme le reste : décoratives pour un lecteur d'écran, elles restent lues par tous les voyants. L'illustration de l'accroche existe en **deux compositions** (large et compacte) : une seule mise à l'échelle rendrait ses étiquettes illisibles sur téléphone. **Le dessin doit être centré dans son `viewBox`, pas seulement la balise `<svg>` dans son conteneur** : la planche « Automatiser » occupait x 112→662 dans un cadre 0→684, soit 45 unités de décalage vers la droite — invisible en grand, flagrant sur téléphone. Corrigé en décalant la fenêtre (`viewBox="45 0 684 420"`) plutôt que vingt coordonnées. Contrôle : comparer `svg.getBBox()` aux bornes du `viewBox`, les deux marges doivent être égales.

## Réservation (booking) — seul code serveur dynamique

Système natif qui a remplacé Cal.com (moins de dépendance tierce). **Pas de section dédiée** : le RDV s'ouvre dans une **modale `<dialog>`** depuis les CTA « Réserver un appel » — en-tête, menu mobile, contact, pied de page et pages dédiées. `SiteShell` monte la modale sur chaque route, donc le CTA marche partout.

- **Flux** : `Booking.tsx` (serveur, résout les labels) monte `BookingModal.tsx` (client, `<dialog>` natif) **une seule fois** après le Footer, sur l'accueil comme sur chaque page dédiée. Les CTA appellent `openBooking()` (store `useBookingModal`, `useSyncExternalStore` sans Provider) — depuis un composant serveur, via `BookingButton` (hero, contact, pages dédiées) ; `Btn` accepte `href` **ou** `onClick`. La modale contient `BookingClient.tsx` → calendrier Lun-Ven 9h-17h **Europe/Brussels** (`BOOKING` est la source unique : le JSON-LD `openingHoursSpecification` en dérive, il ne peut plus annoncer d'autres horaires que ceux réellement proposés), créneaux 30 min, fenêtre 3 semaines (config `BOOKING`). Le `GET /api/availability` n'est appelé **que quand la modale est ouverte** (prop `active`), jamais au chargement de page. Le visiteur choisit un créneau, remplit nom/email/téléphone/visio|appel + Turnstile → `POST /api/bookings`. Le propriétaire reçoit un email avec liens signés **Confirmer/Refuser** → page **2-temps** `/[lang]/booking/[action]` (GET affiche un bouton → POST exécute, anti-prefetch) → `/api/bookings/{confirm,refuse}`. La confirmation génère le lien kMeet (`kmeet.infomaniak.com` — instance Jitsi d'Infomaniak, room anonyme créée à la première connexion : lien unique, tout le monde est modérateur. L'API `POST /1/kmeet/rooms` existe mais n'est **pas** utilisée : elle imposerait un token, un scope `kmeet` et un appel réseau faillible dans le flux de confirmation) et envoie un email **au client ET au propriétaire**, chacun avec une **pièce jointe `.ics`** (`lib/booking/ics.ts`, VEVENT RFC 5545, ajoutable dans tout agenda) portant le lien visio en lieu.
- **Chargement différé** : `BookingModal` importe `BookingClient` via `next/dynamic` et ne le rend que si `session > 0`. Calendrier, formulaire et Turnstile ne sont donc montés qu'au premier clic sur « Réserver un appel », pas à chaque visite. `session` ne redescend jamais : une fois montée, la modale le reste, y compris pendant sa transition de fermeture. Mesuré sur réseau lent : modale ouverte en 316 ms avec titre et état de chargement, calendrier à 1,1 s — pas de flash vide.
- **La confirmation ne se ferme pas toute seule.** La modale se refermait 2,5 s après l'envoi : personne qui lit lentement, à la loupe ou au lecteur d'écran n'avait le temps de la lire (WCAG 2.2.1, Timing Adjustable). Le focus est désormais posé sur le message, et c'est le visiteur qui ferme.
- **Les créneaux sont groupés par demi-journée** (`slotPeriod`, pur et testé) : dix-sept boutons alignés d'un bloc ne se lisent pas. Chaque groupe est un `role="group"` nommé par son titre visible via `aria-labelledby`, jamais par un `aria-label` qui doublerait le texte. La coupure se fait à midi **en heure de Bruxelles**, pas en UTC — en été, 11:00Z est déjà l'après-midi, et c'est testé dans les deux sens.
- **La rangée des jours n'affiche pas sa barre de défilement** (`scrollbar-width: none` + `::-webkit-scrollbar`) : elle coupait la rangée en deux sans rien apprendre, les jours se faisant glisser au doigt et se tabulant au clavier. Elle porte en revanche un `padding-block` : dans un défileur, une pastille survolée se soulève de 2 px et son contour de focus déborde de 5 px — sans cette place, le défileur les rogne.
- **Modale** : `<dialog>` natif (`showModal()` → focus-trap, Esc, top-layer gratuits), fond opaque dérivé du thème, titre et fermeture dans un en-tête qui reste visible au défilement, animée via `@starting-style` + `transition-behavior: allow-discrete` (`opacity`/`transform`/`overlay`/`display`). Clic backdrop (`target === dialog`) ou `close` event → `closeBooking()`. `body { overflow: hidden }` quand ouverte.
- **Synchronisation agenda (lecture seule)** : `GET /api/availability` croise **deux sources** — les demandes déjà reçues (table D1) et les agendas publiés par le studio. `BOOKING_CALENDAR_ICS_URL` contient une ou plusieurs URLs iCalendar séparées par des virgules (kCalendar Infomaniak : _Partager publiquement un agenda_ → URL de la forme `https://sync.infomaniak.com/calendars/<compte>/<uuid>?export`, qui répond en `text/calendar` sur un simple GET sans authentification). `calendar.ts` les récupère (timeout 4 s, plafond 2 Mo vérifié sur `Content-Length` avant lecture du corps, **cache mémoire de 2 min** — sans lui chaque ouverture de modale paie un aller-retour vers l'agenda, ~100 ms mesurés, et le service tiers encaisse une requête par visiteur), `ical.ts` les analyse. **Pas de CalDAV, pas d'OAuth, pas de token à renouveler** : un simple GET, ce qui passe sans friction sur workerd.
  - **Accès authentifié à privilégier.** Le serveur est un SabreDAV : l'URL `?export` répond **200 sans aucune authentification** (quiconque la détient lit l'agenda), tandis que la collection CalDAV répond `401 WWW-Authenticate: Basic realm="sabre/dav"`. Renseigner `BOOKING_CALENDAR_AUTH` (`identifiant:mot-de-passe-application`) permet donc de **révoquer le partage public** et de lire l'agenda par Basic Auth. Chez Infomaniak, générer un _mot de passe d'application_ dédié — révocable seul, et obligatoire dès que la 2FA est active. Sans cette variable, le comportement reste celui d'une URL publique.
  - L'agenda branché est l'agenda **principal du studio** (« Nicolas Wieckiewicz »), pas un agenda dédié : ce qui y figure fait foi pour la disponibilité, sans double saisie. L'URL est un secret Worker, mais elle expose le contenu de l'agenda publié — le compte kCalendar est strictement professionnel, le privé vit ailleurs.
  - Conséquences d'un agenda principal, à connaître avant de s'étonner : un événement **journée entière** bloque la journée complète (anniversaires, jours fériés importés) — le marquer « Disponible » dans kCalendar (`TRANSP:TRANSPARENT`) le neutralise. Une **invitation déclinée** qui reste dans l'agenda bloque encore : la supprimer. Un événement **provisoire** (`STATUS:TENTATIVE`) bloque volontairement — un « peut-être » ne se vend pas comme libre.
  - `ical.ts` est **pur et testé** (19 tests) : dépliage RFC 5545, `DTSTART`/`DTEND`/`DURATION`, `TZID` et journées entières, `RRULE` (DAILY/WEEKLY/MONTHLY/YEARLY avec INTERVAL, COUNT, UNTIL, BYDAY), `EXDATE`, et exclusion de `STATUS:CANCELLED` et `TRANSP:TRANSPARENT`. Les formes rares (BYSETPOS, BYMONTHDAY multiples) ne sont pas dépliées — l'occurrence de base reste bloquée, jamais l'inverse.
  - **Le dépliage démarre près de la fenêtre, pas au DTSTART** (`skipToWindow`). L'agenda branché est l'agenda principal du studio : il porte des séries anciennes. Avec un plafond de 400 itérations, une récurrence **quotidienne** ou **hebdomadaire par jours nommés** commencée il y a plus de 400 pas n'atteignait jamais la fenêtre de trois semaines — elle cessait de bloquer, en silence et dans le sens dangereux : le créneau restait réservable alors qu'il est pris. Le saut se fait par **multiples entiers d'intervalle** pour garder la phase de la série, et seulement quand il n'y a pas de `COUNT` (compter exige de partir du début). MONTHLY et YEARLY gardent 33 ans de marge, on n'y touche pas.
  - **Dégradation volontairement ouverte** : agenda injoignable, lent ou illisible → aucune plage remontée, tous les créneaux restent réservables. Fermer bloquerait toute prise de rendez-vous sur une panne tierce, alors que le pire cas ici est une demande à refuser — ce que le flux de confirmation permet déjà. Ne pas inverser ce choix sans mesurer ce qu'on perd.
  - La synchro est **unidirectionnelle**. Le `.ics` envoyé à la confirmation va dans l'autre sens (réservation → agenda) : rien n'écrit dans kCalendar.
- **Logique pure testable** dans `lib/booking/*.ts` (`slots`, `schema` Zod, `token` HMAC, `meeting`, `email`, `format`, `ics`, `record`) — couverte par vitest, **sans réseau ni DB**. Effets de bord non testés : `db.ts`, `mailer.ts`, `turnstile.ts`, `actions.ts`. Toute nouvelle logique métier va dans `lib/booking/` pour rester testable — c'est pour ça que le mapping ligne SQL → domaine vit dans `record.ts` (pur) et pas dans `db.ts`.
- **Runtime** : Cloudflare Workers (workerd) via OpenNext. Aucun `export const runtime` : le flag `nodejs_compat` couvre tout ce que le code utilise (`node:crypto` complet depuis avril 2025, `node:buffer`, et `process.env` peuplé automatiquement avec les vars + secrets). `GET /api/availability` + la page action déclarent `dynamic = "force-dynamic"`.
- **DB** : Cloudflare **D1** (SQLite), binding `DB` déclaré dans `wrangler.jsonc`, typé par `cloudflare-env.d.ts` (généré par `wrangler types`, gitignored, régénéré en `postinstall` — ne jamais l'écrire à la main). Accès via `getCloudflareContext({ async: true })` dans `lib/booking/db.ts`. La DDL vit dans `migrations/` et s'applique avec `wrangler d1 migrations apply`, jamais à la main dans le dashboard. **Pas d'ORM** : 2 tables, ~6 requêtes préparées.
- **Dates en SQLite** : pas de type date. Tout est stocké en **ISO 8601 UTC** (`2026-01-14T07:00:00.000Z`), ce qui trie et compare lexicographiquement — d'où le `BETWEEN` sur `slotStart`. Toujours passer par `slotKey()` (`record.ts`) avant d'écrire : deux écritures du même instant dans deux formats différents contourneraient l'index unique.
- **Anti-double-booking** : index UNIQUE **partiel** `Booking(slotStart) WHERE status IN ('pending','confirmed')` (`migrations/0001_create_booking.sql`). Insert + catch `UNIQUE constraint failed` → `insertBooking` renvoie `null` → 409. Jamais de check-puis-insert. Un refus libère le créneau.
- **Transitions de statut** : `settleBooking` fait `UPDATE ... WHERE id = ? AND status = 'pending'` et lit `meta.changes` — l'idempotence est garantie par la DB, pas par un read-then-write qui perdrait la course en cas de double clic.
- **Anti-abus** : Cloudflare Turnstile (vérif serveur `turnstile.ts`, hors CSP navigateur) + rate limit D1 par IP **hashée HMAC** (table `RateLimitHit`, RGPD : jamais d'IP en clair ; `clientIp` lit `cf-connecting-ip` en priorité, non spoofable derrière Cloudflare) + honeypot champ `company` (composant `Honeypot`, partagé par les deux formulaires). Chiffres à répercuter dans `lib/legal.ts` s'ils changent : **5 envois par heure glissante**, empreintes **effacées après 24 h** (`WINDOW_MS`, `MAX_PER_WINDOW`, `RETENTION_MS` dans `ratelimit.ts`). La purge s'exécute **à l'écriture du hit suivant**, pas sur une horloge : la page légale le dit ainsi (« effacées au premier envoi suivant leur vingt-quatrième heure ») plutôt que de promettre une suppression à l'heure près que le code ne tient pas.
- **Une IPv6 est ramenée à son préfixe /64** (`ipKey`, pur et testé) avant d'être hachée : un abonné reçoit couramment un /64 entier, donc hacher l'adresse complète rendait les cinq envois par heure contournables en changeant d'hôte dans son propre réseau. Une IPv4 encapsulée (`::ffff:…`) est identifiée par son adresse v4, sinon tous ces clients partageraient un seul seau.
- **L'accusé de réception ne reprend aucun mot du formulaire.** Il part avant toute validation, vers l'adresse que l'auteur du formulaire a saisie : y insérer le `name` permettait d'envoyer le texte de son choix à l'adresse de son choix, signé par le domaine du studio. La salutation est donc neutre, exactement comme l'accusé du formulaire de demande. La confirmation, elle, part après validation par le propriétaire : elle peut nommer le client.
- **Un `.ics` est un format à lignes, donc une cible d'injection.** `escapeText` traite maintenant le **retour chariot seul** (un analyseur tolérant y voit une fin de ligne, donc une propriété forgée dans l'agenda du propriétaire) et les paramètres `CN=` passent par `escapeParam`, qui met la valeur entre guillemets et neutralise `"`, `:` et `;` — un paramètre vit **avant** le `:` qui ouvre la valeur. Défense en profondeur à la frontière : le schéma refuse tout caractère de contrôle dans `name` (`\p{Cc}`), sans rejeter les noms composés, accentués ou apostrophés.
- **Un jeton Turnstile ne sert qu'une fois** : après un échec d'envoi, les deux formulaires remontent le widget (`key={attempt}`). Sans ce remontage, le second essai repart avec un jeton consommé et échoue à la vérification, sans que le visiteur comprenne pourquoi. Le formulaire de demande réutilise les trois (même table `RateLimitHit`, donc un quota horaire commun aux deux formulaires).
- **Invitations agenda** : trois envois portent un `.ics`. La **demande** envoyée au propriétaire en porte un en `STATUS:TENTATIVE` / `SEQUENCE:0` — il tient le créneau dans l'agenda avant même la confirmation, et `ical.ts` traite déjà un provisoire comme occupé ; la **confirmation** repart avec le **même UID** en `SEQUENCE:1` / `CONFIRMED`, ce qui remplace l'événement au lieu de le dupliquer chez un client conforme à la RFC 5545. Si refus, l'événement provisoire reste dans l'agenda et doit être supprimé à la main : c'est dit dans le corps de l'email, parce qu'un provisoire oublié bloquerait le créneau pour tout le monde. L'événement du propriétaire porte le nom du client en titre et ses coordonnées en description ; celui du client reste neutre.
- **Boutons d'email** : `mailButton()` et `mailLink()` (`email.ts`) sont les deux seules formes d'action d'un email — un `<a>` stylé en ligne, la seule que tous les clients mail rendent. Confirmer/Refuser et « Ajouter à Google Agenda » passent par là ; un lien laissé nu s'affiche en bleu système et sort de la charte.
- **Une seule adresse pour le studio** : `ownerAddress()` (`mailer.ts`), avec repli sur l'adresse publique. Elle était résolue à trois endroits avec deux règles : sans `BOOKING_NOTIFY_EMAIL`, une demande de formulaire partait quand même, mais une **réservation n'avertissait personne** — enregistrée, sans email, sans erreur. Le repli est testé.
- **Emails** : API HTTP **Brevo** (`POST /v3/smtp/email`, `mailer.ts`) — Workers ne peut pas ouvrir de socket SMTP. Expéditeur = un sender vérifié Brevo (`BREVO_SENDER_EMAIL`), `replyTo` sur `EMAIL` sauf si le `Mail` en fournit un (`replyTo`, utilisé par la notification du formulaire de demande pour répondre directement au prospect). Les `.ics` partent en pièce jointe base64. Un envoi dont l'échec ne doit pas faire échouer la requête passe par **`sendMailOrReport`**, jamais par un `catch` muet : l'erreur part dans Workers Logs **et** dans Bugsink — une réservation enregistrée dont la notification s'est perdue est un rendez-vous que personne ne voit arriver.
- **Liens d'action** : HMAC `BOOKING_ACTION_SECRET` (`token.ts`, comparaison `timingSafeEqual`). Routes `confirm`/`refuse` = un seul helper `runBookingAction` (`actions.ts`). Idempotent, refusé si créneau passé.
- **Formulaire de demande** (« Montrez-moi la tâche », « Décrivez la panne ») : `LeadForm.tsx` (client) → `POST /api/leads` → notification au propriétaire (`BOOKING_NOTIFY_EMAIL`, à défaut `EMAIL`, en français, `replyTo` = prospect) + accusé de réception au prospect. Champs : tâche (20–2000 car.), temps perdu par semaine (facultatif, masqué sur le dépannage), email, `source` (`home` ou l'id de la page dédiée — mesure quelle page convertit). **Rien n'est stocké** : l'email est la seule trace, donc un échec de la notification renvoie 502 et le prospect voit l'erreur avec l'adresse de contact ; l'accusé de réception reste best-effort et **ne reprend jamais le texte saisi** (sinon le formulaire relaierait n'importe quel contenu vers n'importe quelle adresse). Turnstile n'est monté qu'au **premier focus** dans le formulaire : aucun script tiers au chargement de page. Un jeton Turnstile ne sert qu'une fois : après un échec, le widget est remonté (`attempt`). Logique pure dans `lib/leads/` (`constants` sans zod, importable côté client ; `schema` ; `email`), testée.
- **Setup (une fois)** : `pnpm db:migrate` (local) et `pnpm db:migrate:remote` (prod), puis l'env — voir `.env.example` (`NEXT_PUBLIC_TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY`, `BREVO_API_KEY`, `BREVO_SENDER_EMAIL`, `BOOKING_NOTIFY_EMAIL`, `BOOKING_ACTION_SECRET`, `IP_HASH_SECRET`, `BOOKING_CALENDAR_ICS_URL` — cette dernière facultative : sans elle la synchro agenda est simplement inactive). En prod ce sont des secrets Workers (`wrangler secret put`, ou `wrangler secret bulk` pour les neuf d'un coup), pas des `vars` — posés le 2026-10-09, `wrangler secret list` les vérifie. Clés de test Turnstile fournies pour le dev.
- **La clé publique du widget vit dans le dépôt** (`lib/turnstile.ts`), pas seulement dans l'environnement. Cloudflare **redéploie tout seul à chaque push** (Workers Builds est branché sur le dépôt) et son build n'a évidemment pas le `.env` local : chaque déploiement automatique repartait donc avec `siteKey:""` et une réservation morte. Une _sitekey_ Turnstile est publique par construction — elle est lisible dans le HTML de chaque page — contrairement à `TURNSTILE_SECRET_KEY`, qui reste un secret Worker. La variable d'environnement garde la priorité, pour une rotation ou une clé de test. Le contrôle de fumée échoue si `siteKey:""` réapparaît.
- **`NEXT_PUBLIC_TURNSTILE_SITE_KEY` est une variable de _build_**, pas un secret Worker : elle est figée dans le bundle par `pnpm build`. Le worker déployé le 2026-09-23 a été construit sans elle — le HTML servi contient `siteKey:""`, le widget ne peut pas se monter, le bouton d'envoi reste désactivé et **aucune réservation ne part**, sans la moindre erreur visible. Symptôme : « rien ne se passe quand je réserve ». Contrôle en une commande : `curl -s https://silexio.be/fr | grep -o 'siteKey[^,}]*'`. Un `.env` complet au moment du build est donc une condition de déploiement, pas un détail.
- **Contenu** (`lib/data.ts`) : `I18N.form` porte les libellés communs aux deux formulaires (facultatif, envoi, anti-robot, erreurs de quota/captcha/validation) ; chaque formulaire fusionne ce dictionnaire avec le sien (`BookingLabels`, `LeadLabels`). `I18N.booking` (UI, résolu en bloc via `resolveDict` → type `BookingLabels`), `BOOKING_EMAILS` (templates FR/EN, placeholders `{...}` + échappement HTML dans `email.ts`), `BOOKING_ACTION` (page action). Pas de chapitre `booking` dans `CHAPTERS` (c'est une action, pas une section). Pages action en `noindex` + disallow robots.

## CSS — décision structurante

`app/globals.css` est un design system BEM écrit à la main, en **18 sections numérotées** (sommaire en tête de fichier) : jetons, base, mise en page et typo, actions, animations, puis un bloc par zone de l'interface. **Ne pas le réécrire en utilities Tailwind** — Tailwind 4 ne sert que son preflight.

- **Jetons, un seul endroit.** Couleurs en hexadécimal (`--bg`, `--surface`, `--raised`, `--border`, `--border-strong`, `--heading`, `--text`, `--muted`, `--accent`, `--accent-ink`, `--on-accent`, `--error`, `--success`, `--bezel`, les éclats et la marque) ; le thème sombre redéfinit les mêmes variables sous `[data-theme="dark"]`. Typo : `--font-title` / `--font-body` et l'échelle `--fs-h1` → `--fs-small`. Espacement `--s-1` à `--s-7` (plus `--s-1-5`), rayons `--radius-field|frame|panel|pill`, cible tactile `--tap`, hauteur de contrôle `--control-h`, mouvement `--dur-fast|slide|reveal`. **Aucune valeur de design en dur** dans une règle ou un composant : si une valeur manque, c'est un jeton à ajouter.
- **Hiérarchie des actions** : un seul bouton plein par écran, puis les pilules, puis les liens soulignés. La pilule WhatsApp portait un contour d'encre et une graisse 700 : elle passait devant le bouton principal dans un pied de page calme. Elle est redescendue d'un cran (`--border-strong`, graisse 600) — au-dessus des réseaux, sous un vrai CTA.
- **Le survol d'un bouton doit se voir.** Le plateau d'encre virait au noir pur : un changement invisible. Il **s'éclaircit** maintenant (`--accent-hover` `#3a332e`), dans le même sens qu'en thème sombre, et le texte y tient 10,5:1. Le repos reste sombre : sur un papier clair, l'élément le plus foncé est celui qui attire, pas l'inverse.
- **Primitive de contrôle** : une seule déclaration porte le fond, le rayon et le trait du champ, du créneau choisi et de la pastille de créneau. Trait d'un contrôle = `--stroke-control`, y compris `.icon-btn` et le marqueur de FAQ, qui gardaient un `1px` écrit à la main — un contour qui ne suit pas le jeton reste seul le jour où le jeton bouge. Elle vise `.field input:where(:not([type="radio"], [type="checkbox"]))` : sans cette exclusion, un bouton radio héritait de `width: 100%` et de `min-height: var(--control-h)`, le widget natif s'étirait sur toute la hauteur de sa pastille et dessinait une barre verticale. **Un `<select>` doit porter `appearance: none`** et sa flèche redessinée, sinon il rend le widget du système et ignore rayon et trait — c'est le champ qui « n'a pas le même arrondi que les autres ». Aucun composant ne redéclare plus `--radius-panel` ni `background: var(--surface)` : ils appartiennent au groupe « surface », et le redire rouvrait la porte à la divergence.
- **Primitives partagées** (sélecteurs groupés, zéro duplication) : typo (`.display`, `.title`, `.subtitle`, `.heading-sm`, `.lead`, `.eyebrow`, et le groupe « texte secondaire » qui porte `--fs-small` + `--muted` pour une douzaine de classes), surface (`.panel` et les blocs qui partagent son fond et son rayon), actions (`.btn`, `.link` + `--accent`/`--action`, `.pill`, `.chip`, `.icon-btn`, `.icon`), formulaire (`.form`, `.field`, `.notice`, `.honeypot`, `.captcha`) commun à la demande et au rendez-vous, et les pastilles de choix du calendrier qui **sont** des `.pill`.
- **Pan coupé des boutons** : `--facet` (clip-path dérivé de `--cut`) est peint par `.btn::before`, pas par un `clip-path` sur le bouton — un clip-path rognerait aussi le contour de focus clavier. Taille via `--btn-h`/`--btn-pad`, variante `.btn--compact` pour l'en-tête ; pas de surcharge `.x .btn` par contexte.
- **Échelle typographique** : H1 `clamp(34px, 1.6rem + 2.4vw, 60px)`, titre de section `clamp(30px, 1.25rem + 1.8vw, 46px)`, carte 22→28, corps 17→18, légende 15 (minimum). Interligne 1,6 pour le texte, 1,1–1,2 pour les titres. Un h2 ne doit jamais dépasser le h1 : si l'un bouge, rebaser l'autre.
- **Règles de lecture** (charte A3, sources BDA / WCAG 1.4.8 / NN-g) : paragraphes alignés à gauche, jamais justifiés, 70 caractères par ligne au plus ; pas d'italique ni de capitales — le gras sert à insister ; seuls les liens sont soulignés ; centré seulement pour un titre et une phrase courte ; aucun blanc pur ni noir pur.
- **Contraste mesuré** (calcul WCAG sur les hex, les deux thèmes) : texte 11,2:1 clair / 11,7:1 sombre, secondaire au pire 5,3 / 5,4, accent en texte au pire 13,5 / 13,0, texte sur bouton 14,9 / 14,3, étincelle sur le bouton encre 9,7. **`--border-strong`** (3,6:1 clair, 3,9:1 sombre sur la surface) est le contour des champs, pastilles et points du diaporama : un contour de composant doit tenir 3:1 (WCAG 1.4.11), ce que `--border`, purement décoratif, ne tient pas. Ne rien éclaircir sans re-mesurer.
- **Pas de verre dépoli.** L'en-tête, le menu et la modale ont un fond **opaque** dérivé du thème : lisible au-dessus de n'importe quel contenu, sur tout navigateur, et plus aucune dépendance à `backdrop-filter` (ni à l'ordre de ses préfixes, ni au `@supports` de repli).
- **`overflow-x: clip` sur `body`, jamais `hidden`** : `hidden` ferait du body un conteneur de défilement et l'en-tête `sticky` se collerait à lui, donc ne tiendrait plus.
- Les animations pilotées par le défilement sont gardées derrière `@supports (animation-timeline: …)` — sans ce garde, Firefox affiche l'état final figé.

## Animations

**Le projet n'a pas de bibliothèque d'animation.** Tout est du keyframe CSS ; le seul JS restant est le script d'amorçage du layout. Ne pas réintroduire de dépendance d'animation sans mesurer ce qu'elle coûte au LCP simulé (cf. § Plafond de performance).

### Le script d'amorçage — `lib/boot.ts`

Le `<script>` inline du `<head>` est **écrit en TypeScript**, pas en chaînes de caractères. `BOOT_SCRIPT` concatène cinq fonctions sérialisées par `toString()` : `applyTheme`, `armReveals` (les deux observateurs), `aimStoneParts`, `armKnapClick`, `stonePhysics`.

- **Pourquoi** : ni tsc ni eslint ne lisent une chaîne. Un `aimFacets()` écrit pour `aimParts()` a traversé le build, le lint et la revue, et coupait en silence la retaille de la marque **et toute la physique** — un `ReferenceError` qui interrompt l'IIFE sans rien afficher. Deux audits indépendants l'ont trouvé le même jour, par lecture. Depuis, le compilateur le trouve en une seconde.
- **Chaque fonction doit rester autonome** : aucun import, aucune variable de module, les seules entrées passent en paramètres de l'appel (`(${fn})(${MARK_CENTER.x},${MARK_CENTER.y})`). Une variable libre serait renommée par le bundler et la fonction sérialisée casserait.
- **Gain mesuré** : le minificateur mange les noms locaux, donc 3 491 octets bruts / 1 409 gzip contre 4 982 / 1 640 pour la version à la main.
- `lib/boot.test.ts` exécute le script sur un DOM minimal, dans les deux branches de `readyState`, et **atteint réellement chaque fonction** : `matchMedia` répond selon la requête (sinon la physique sort à sa première ligne), le gestionnaire de clic est appelé avec une cible, et `requestAnimationFrame` exécute quelques images (sinon l'intégrateur n'est jamais évalué). Chaque garde a été vérifiée en réintroduisant une faute.

- **Le mouvement est activé sous `@media (prefers-reduced-motion: no-preference)`**, il n'est pas désactivé après coup. C'est l'inverse de l'ancienne approche : il n'y a plus de liste d'animations à tenir à jour ni de `!important` pour les annuler, et une animation ajoutée plus tard ne peut pas laisser un bloc invisible chez quelqu'un qui a demandé moins de mouvement. Le bloc `reduce` ne coupe plus que les transitions d'état.
- Reveals (sous la ligne de flottaison) : `components/ui/Reveal.tsx` est un **composant serveur** qui n'émet qu'un `<div data-reveal>` + `--d` (délai). L'état masqué est en CSS, le déclenchement vient du script inline qui pose `data-in`. Rien n'est monté côté client. `suppressHydrationWarning` sur ce div est voulu : le script pose `data-in` avant l'hydratation sur les blocs déjà visibles.
- `data-reveal-js` est posé par ce même script : **sans JS, l'attribut n'existe pas et le contenu reste visible**.
- Un **second** observateur (`data-visible`, marge de 120 px) suit l'entrée **et la sortie** d'écran, sur les `[data-reveal]` et sur `.chore-map` : c'est lui qui met en pause les démonstrations hors champ. Il ne se désabonne jamais, contrairement au premier.
- Le script écrit sur le DOM **avant l'hydratation** : tout élément qu'il touche porte `suppressHydrationWarning` — le div de `Reveal`, la planche `.chore-map` (qui reçoit `data-visible`) et chaque `.knap__part` (qui reçoit ses vecteurs). Sans ça React signale un écart « qu'il ne corrigera pas », à chaque chargement.
- Accroche (au-dessus de la ligne de flottaison) : `HeroLines.tsx` (keyframe `line-rise`) et la classe `.hero-reveal` sont **rendues côté serveur**. **Ne jamais remettre l'accroche derrière une animation gatée par l'hydratation** : un LCP à 9,7 s avait été mesuré ainsi, dont 93 % de render delay.
- Diaporama : les diapositives voisines s'estompent via `animation-timeline: view(inline)` — aucun JS, et rien ne se dégrade là où la fonctionnalité manque.
- Le canvas animé de la section Contact (`Neurons.tsx`) et le bandeau défilant de technos ont été **supprimés** : du JS et du mouvement pour une page qui vise un patron de PME. Ne pas les réintroduire.

## Thème

`data-theme` sur `<html>`, posé avant le paint par le script inline du layout (anti-FOUC), persisté dans `localStorage("silex_theme")`. Le toggle (NavClient) écrit le DOM directement dans `document.startViewTransition` — **pas de state React pour le thème** (évite hydration mismatch + flushSync). Icônes lune/soleil swappées en CSS via `[data-theme]` (`Icon` + `.theme-toggle__moon|sun`). Les couleurs de marque hors CSS — barre du navigateur, manifeste PWA, emails — viennent de `lib/brand.ts` : c'est le seul endroit où un hex vit en TypeScript. `suppressHydrationWarning` sur `<html>` **et `<body>`** est requis (le `<body>` neutralise les attributs injectés par des extensions navigateur — ex. ColorZilla `cz-shortcut-listen` — qui sinon provoquent un hydration mismatch console).

Des concurrents labellisés affichent « 50 % remboursé » ; ce n'est pas un oubli à corriger côté site, c'est un argument qu'on n'a pas. Ne pas l'écrire sur le site, ne pas le re-proposer.
- La TVA est celle de la coopérative, partagée par tous ses membres : elle reste hors du JSON-LD (pas de `vatID`), sinon Google confond l'entité Silexio avec des milliers d'autres. Idem `telephone` : le numéro est privé, seul `LEGAL.whatsappUrl` (lien d'invitation `wa.me/message/…`) est publié — **ne jamais écrire le numéro dans ce dépôt, il est public sur GitHub**.
- `LEGAL` est typé explicitement `string` par champ (pas `as const`, sinon le narrowing d'un champ vide tombe sur `never`) : un champ vide masque son affichage. Ne jamais inventer ces valeurs.
- JSON-LD dans `lib/seo.ts`, en **deux fonctions volontairement séparées** :
  - `structuredData(lang)` — identité du site, injectée par le **layout** donc présente sur toutes les pages du segment : `Person` (+ `hasOccupation`, 36 entrées `knowsAbout` **dans la langue de la page** — `KNOWS_ABOUT` est un `Record<Locale, string[]>`, les noms de technologies étant partagés par `TOOLS` puisqu'ils ne se traduisent pas) + `ProfessionalService`/`LocalBusiness` (geo, serviceArea, areaServed, hasOfferCatalog dérivé de `OFFERS` avec `PriceSpecification` HTVA — `minPrice` pour un prix « dès », `UnitPriceSpecification` mensuelle pour le suivi —, horaires) + `WebSite`.
  - `faqStructuredData(lang)` — `FAQPage` dérivé de `FAQ`, injecté **uniquement par `app/[lang]/page.tsx`**, la seule page qui affiche les questions. Il vivait dans le graphe du layout et se retrouvait donc émis sur `/[lang]/legal`, qui ne porte aucune FAQ : Google exige que les données structurées décrivent le contenu **visible** et traite l'écart comme du spam de données structurées. **Toute nouvelle entité liée à une section précise doit suivre ce modèle**, pas rejoindre le graphe du layout.
- La FAQ utilise des `<details>` natifs : le contenu reste dans le HTML même replié, donc indexable. Ne pas la remplacer par un accordéon JS qui monterait le contenu à l'ouverture.
- `robots.ts`, `sitemap.ts` (accueil, `/legal` et les 6 pages dédiées par locale, avec alternates), `manifest.ts` (icônes `public/icon_x*.png`). **Pas de `lastModified`** : `new Date()` au build datait chaque URL du dernier déploiement, y compris celles qui n'avaient pas bougé, et Google ignore un lastmod systématiquement faux. Mieux vaut ne rien annoncer que annoncer faux.
- Hors code, décisif : fiche **Google Business Profile** (profil service-area, adresse masquée) et cohérence NAP avec les annuaires belges. Aucun réglage on-page ne les remplace.
- Headers sécurité dans next.config.ts. CSP : `script-src 'unsafe-inline'` est requis par les scripts inline RSC de Next en SSG — un nonce forcerait le rendu dynamique. Ne pas « durcir » sans comprendre ça. `'unsafe-eval'` est ajouté **en dev uniquement** (`isDev` dans next.config.ts) pour le tooling de debug de React ; la prod reste stricte (React n'utilise jamais eval en prod). Turnstile ajoute `https://challenges.cloudflare.com` à `script-src` + une directive `frame-src` (allowlist de domaine, pas de nonce). `connect-src` reste `'self'` : aucun beacon tiers, aucune télémétrie externe — ne pas en réintroduire sans rouvrir la CSP en conscience.

## Déploiement (Cloudflare Workers)

- **Cloudflare déploie tout seul depuis le dépôt** (Workers Builds). Un push sur **n'importe quelle branche** déclenchait un déploiement du Worker **de production** : le 2026-10-10, un push sur `dev` a remplacé la prod par un build sans `.env`. Un environnement `preview` existe désormais dans `wrangler.jsonc` — Worker `portfolio-preview`, base `portfolio-booking-preview`, migrations par `pnpm db:migrate:preview` — et `pnpm deploy:preview` le déploie à la main. **Réglage restant côté tableau de bord** : Workers Builds → contrôle des branches → les branches autres que `main` doivent construire avec `--env preview`. Sans ce réglage, `dev` continue d'écraser la production.
- Le build de Cloudflare n'a **jamais** le `.env` local : tout ce qui doit être figé dans le bundle vit dans le dépôt (cf. `lib/turnstile.ts`) ou dans les variables de build de Workers Builds. Les secrets serveur, eux, restent des secrets Worker.

- `wrangler.jsonc` : `nodejs_compat` (obligatoire pour OpenNext, et c'est lui qui fournit `node:crypto` + `process.env`), `compatibility_date` ≥ 2024-09-23, binding D1 `DB`, assets `.open-next/assets`, `observability.enabled` (Workers Logs, gratuit).
- `open-next.config.ts` : `staticAssetsIncrementalCache` — le cache ISR est servi depuis les assets statiques, donc pas de KV ni de queue de revalidation à provisionner.
- `initOpenNextCloudflareForDev()` en bas de `next.config.ts` : c'est ce qui injecte les bindings dans `next dev`. Sans lui, `getCloudflareContext()` throw en dev et le booking dégrade en silence.
- Les analytics Vercel (`@vercel/analytics`, `@vercel/speed-insights`) ont été retirés : ils ne collectent rien hors Vercel. Les logs d'exécution passent par Workers Logs, les erreurs par Bugsink (§ Observabilité).

## Observabilité (Bugsink self-hosted)

**Bugsink** sur `sentry.silexio.be` parle le protocole Sentry. Le partage est asymétrique et volontaire : le SDK officiel côté **serveur**, un reporter écrit à la main côté **navigateur**.

### Serveur — `@sentry/nextjs`

- `instrumentation.ts` (`register` + `onRequestError`, et un warn au boot listant les env vars manquantes) et `sentry.server.config.ts`. Pas de config edge : OpenNext exécute tout en runtime `nodejs`. Supporté sur Workers via OpenNext grâce à `nodejs_compat` + `compatibility_date` ≥ 2025-08-16 (qui apporte `https.request`, requis par le transport Sentry).
- `tracesSampleRate: 0` — Bugsink n'ingère **que** des erreurs, les traces seraient jetées à l'arrivée. `sendDefaultPii: false` : les payloads de réservation portent nom, email et téléphone de prospects (Bugsink recommande `true` pour du self-hosted, c'est un choix délibéré du projet, pas un oubli).
- Inerte sans `SENTRY_DSN`.

### Navigateur — reporter maison, pas le SDK

`lib/observability/report.ts` (pur, 17 tests) construit une enveloppe Sentry v7 ; `lib/observability/client.ts` porte les effets de bord (deux écouteurs globaux, `fetch` en `keepalive`) ; `instrumentation-client.ts` l'installe ; `app/global-error.tsx` l'appelle pour ce que `window.onerror` ne voit pas.

- **Pourquoi** : `@sentry/nextjs` pèse 247 Ko bruts / 74 Ko transférés, soit ~30 % du JS de la page. Mesuré : le retirer fait passer le mobile de **84 à 92** et le desktop de **99 à 100**. Le reporter fait ~1 Ko.
- **Gardé** : type, message, pile parsée (dialectes V8 et SpiderMonkey/JavaScriptCore), URL, user-agent, environnement, déduplication par `type|message|frame`, plafond de 8 envois par page (un plantage en boucle ne doit noyer ni Bugsink ni le réseau du visiteur).
- **Perdu, assumé** : breadcrumbs (console, clics, fetch), contexte de route automatique, et la résolution symbolique par debug id — **les piles arrivent minifiées**. C'est le prix des 8 points. Si un jour la symbolication devient nécessaire, la remettre coûtera ce score.
- **L'enveloppe doit porter l'authentification du protocole, sinon Bugsink la jette.** Le relais POSTait l'enveloppe sans en-tête `X-Sentry-Auth` : le serveur répondait **403** et **aucune erreur navigateur n'est jamais arrivée** depuis l'écriture du reporter. Rien ne le signalait — le navigateur ne lit pas la réponse, et la vérification d'alors s'était arrêtée à la forme de l'enveloppe. `envelopeTarget` renvoie donc aussi la **clé publique** du DSN (`https://<clé>@hôte/<projet>`) et refuse un DSN qui n'en porte pas : un relais explicitement inactif vaut mieux qu'un relais qui jette tout en silence. Mesuré après correction : une erreur réelle déclenchée au navigateur donne `POST /monitoring → 202`. Couvert par `app/monitoring/route.test.ts`, qui échoue si l'en-tête disparaît.
- Vérifié de bout en bout au navigateur : 3 erreurs dont un doublon → 2 enveloppes ; 30 erreurs distinctes → plafonné à 8 ; enveloppe en 3 lignes, `event_id` de 32 caractères hex.
- **Ne pas remplacer par un import différé du SDK** : essayé, le chunk se retrouve dupliqué — JS 234 → 340 Ko et TBT 122 → 610 ms. Pire que l'import statique.

### Aucun repli n'est muet — `lib/observability/server.ts`

`reportServerError(error, context)` est le point de passage de **tout `catch` qui renvoie une valeur de repli**. Un repli rend le site résistant et la panne invisible : l'agenda injoignable laisse tous les créneaux ouverts, une notification perdue laisse une demande sans destinataire, et personne n'apprend que ça dure depuis trois semaines. Sont instrumentés : la notification d'une demande (`lead-owner-mail`, celle dont l'échec renvoie 502 au prospect), l'insertion d'une réservation (`booking-insert`), la récupération de l'agenda (`calendar-fetch`, la dégradation reste ouverte mais cesse d'être muette), la vérification anti-robot (`turnstile-verify`, échec fermé : plus aucun formulaire ne part), et tous les envois de `sendMailOrReport`. Le relais `/monitoring` est la seule exception : sa cible est justement ce qui ne répond pas, il écrit donc dans Workers Logs seulement.

Restent volontairement muets : le thème dans le script d'amorçage (un `localStorage` indisponible ne doit rien casser) et le reporter navigateur lui-même (signaler un échec de signalement boucle).

### Relais same-origin

- `app/monitoring/route.ts` reçoit l'enveloppe brute (cap 1 Mo, **vérifié sur `Content-Length` avant de lire le corps** — l'attendre après `arrayBuffer()` revient à l'avoir déjà chargé en mémoire) et la POST vers Bugsink, avec un timeout de 4 s pour qu'un Bugsink lent ne retienne pas le Worker du visiteur ; il, endpoint résolu par `lib/observability/dsn.ts` (pur, testé). Il existe parce que `connect-src 'self'` interdit d'atteindre le host du DSN depuis le navigateur, et parce que le `tunnelRoute` de `@sentry/nextjs` pointe **en dur** sur `ingest.sentry.io` : il ne peut pas atteindre un Bugsink self-hosted. Avant cette correction, **aucune erreur navigateur ne remontait, sans le moindre symptôme**. Coût : une requête Worker par event.
- `global-error.tsx` remplace le layout racine, donc il rend son propre `html`/`body` et ne peut pas résoudre `t()` côté serveur : ses textes vivent dans `lib/i18n/error-page.ts` (4 paires) et non dans `lib/data.ts`, pour ne pas embarquer tout le dictionnaire dans le bundle client. Sa carte réutilise les styles de `.booking-action` via un sélecteur groupé (`.fallback`), pas une copie.
- Source maps : uploadées **seulement si `SENTRY_AUTH_TOKEN`** (+ `SENTRY_URL`/`SENTRY_ORG`/`SENTRY_PROJECT`) par `withSentryConfig`, qui reste en place dans `next.config.ts` pour le serveur. Côté navigateur elles ne servent plus à grand-chose depuis le retrait du SDK, faute de debug id transmis.

## Pièges connus

- **Un `aria-label` ne tient pas sur un `<div>` sans rôle** : il est ignoré, et axe le signale comme attribut interdit. Le conteneur du widget anti-robot porte donc `role="group"`.
- **Ne pas annoncer une sémantique qu'on n'implémente pas.** Le sélecteur de jour du calendrier se donnait `role="tablist"` / `role="tab"` sans panneau associé, sans `aria-controls` et sans navigation aux flèches : un lecteur d'écran annonçait « onglet 1 sur N » et la flèche droite ne faisait rien. Ce sont des boutons bascules (`aria-pressed`), comme les créneaux juste en dessous.
- **Une région `role="status"` montée avec son texte déjà dedans n'est pas annoncée** par tous les lecteurs d'écran, et le bouton d'envoi démonté fait retomber le focus sur `body`. Les deux formulaires posent donc le focus sur le message de fin (`useDoneFocus`).

- Routes typées Next 16 : utiliser les types globaux générés `LayoutProps<"/[lang]">` / `PageProps<"/[lang]">`.
- `as const` sur un objet avec tuples fr/en casse l'inférence de `t()` — typer explicitement (ex. `OFFERS: Offer[]`, ou `satisfies Record<string, Bilingual>` comme `META`).
- Vitest résout l'alias `@/` via `vitest.config.ts` (resolve.alias), pas via tsconfig.
- **Aucune police n'est téléchargée au build** : les deux familles sont auto-hébergées et sous-échantillonnées dans `app/fonts/` (voir son `README.md` pour la procédure de régénération). C'est ce qui rend le build possible sans réseau — ne pas revenir à `next/font/google`, qui téléchargeait au build **et** servait des polices variables d'axe 100-900 pour deux graisses utilisées (120 Ko au lieu de 60).
- **Scripts tiers montés après le chargement** : ne pas utiliser `next/script` pour le widget Turnstile. Il est monté dans la modale, longtemps après l'événement `load` ; React n'exécute jamais une balise `<script>` insérée lors d'un rendu **client** (il le dit en console : « Scripts inside React components are never executed when rendering on the client »). Ni `lazyOnload` ni `afterInteractive` n'injectaient quoi que ce soit — le bouton « Envoyer » restait désactivé pour toujours, **sans la moindre erreur**. `Turnstile.tsx` charge donc l'API lui-même (`document.createElement` + promesse singleton partagée).
- **Cache CSS de `next dev`** : après une édition de `app/globals.css` faite hors de l'éditeur (script, sed), Turbopack sert parfois l'ancienne feuille — les nouvelles règles semblent ignorées alors que le fichier est correct. Symptôme : `getComputedStyle` renvoie les anciennes valeurs. Remède : `rm -rf .next/dev` puis redémarrer. `pnpm build` n'est jamais affecté.
- Une capture n'a pas à suivre le thème du portfolio : Reelmark est servi par sa capture **sombre dans les deux thèmes**, sa version claire étant délavée (affiches quasi invisibles). Choisir la capture qui vend le projet, pas celle qui s'accorde au fond.
- **Cadre de capture** (`.frame`) : l'image porte `aspect-ratio: 16 / 9` et son rayon est **dérivé** (`--radius-frame` − `--frame-pad`), pas écrit deux fois. Pas de chaîne de `height: %` à maintenir : un maillon manquant ferait retomber l'image sur son ratio naturel en laissant une bande vide, et `object-fit: cover` rendrait le diagnostic trompeur.
- **Une `line-height` serrée plus `overflow: hidden` rogne la police.** `.display` impose `1.1` alors que la boîte naturelle de Montserrat fait **1.219 em** (`hhea.ascender - hhea.descender` sur `unitsPerEm`) : le masque des `.line-reveal` coupait 8 px d'accents et de jambages à 38 px, 15 px à 76 px. Corrigé par `overflow-clip-margin: 0.16em`, qui étend la zone de clip **sans toucher à la mise en page** — un padding, lui, aurait déplacé les lignes. Vérifier après tout changement de police ou d'interlignage, et le vérifier **en image** : `getBoundingClientRect` ignore `overflow-clip-margin`, donc un détecteur qui compare les boîtes signale un faux positif.
- **`.sr-only` doit avoir un bloc contenant.** Il est en `position: absolute` : sans ancêtre positionné, il remonte jusqu'au premier qu'il trouve. Un `.sr-only` de bouton placé dans le scroller du carrousel s'est ainsi retrouvé rattaché à un ancêtre **hors** du scroller, qui ne le clippait donc pas : `document.scrollWidth` valait 1288 px pour un viewport de 390, et le mobile dézoomait toute la page. `.btn`, `.link`, `.pill`, `.icon-btn` et `.lang-switch` portent `position: relative` pour cette seule raison. Tout nouvel hôte de `.sr-only` doit en faire autant — le contrôle se fait au runtime, pas à l'œil : lister les `.sr-only` dont l'`offsetParent` est `body`.
- **Un `aria-label` remplace le texte visible, il ne s'y ajoute pas.** Le sélecteur de langue affichait « FR · EN » sous un `aria-label="Passer en anglais"` : nom accessible sans « EN », donc lien inatteignable à la commande vocale (WCAG 2.5.3, niveau A). Lighthouse le signale via `label-content-name-mismatch`, un audit **de poids 0** — invisible derrière un score d'accessibilité à 100. Le libellé passe par un `.sr-only` qui **complète** le texte.
- **Ordre et spécificité en CSS** : une media query **n'ajoute aucune spécificité**. Un bloc `@media (min-width: 900px)` posé _avant_ la règle de base d'un sélecteur de même poids est écrasé par elle. Toujours placer les surcharges responsive **après** les règles de base du composant.
- **Menu mobile : un `<dialog>` ouvert par `showModal()`**, comme la modale de rendez-vous. C'était un `<div>` avec `inert={!open}` : fermé il était correct, mais **ouvert, rien ne retenait le focus** — on tabulait derrière un panneau opaque, dans une page invisible (WCAG 2.4.3 et 2.4.11). Le natif donne l'inertie du reste de la page, le piège de focus, Échap et le retour du focus au bouton d'ouverture, sans une ligne de JavaScript. Trois conséquences à connaître :
  - Les styles du navigateur pour `dialog` (bordure, marge automatique, largeur au contenu, couleur système) doivent être neutralisés, sinon le panneau n'est plus plein écran.
  - `display:none` fermé → `display:flex` ouvert reste piloté par `data-open`, avec `@starting-style` + `transition-behavior: allow-discrete`. La garde desktop `@media (min-width: 900px) { .sheet { display: none } }` va **après** la règle de base — une media query n'ajoute aucune spécificité.
  - **Un dialogue modal laissé ouvert mais masqué par cette garde rendrait toute la page inerte** : un écouteur `matchMedia` le referme au passage des 900 px. Couvert par un test e2e.
- D1 : `cloudflare-env.d.ts` est généré (gitignored) — après toute modif de `wrangler.jsonc`, relancer `pnpm cf-typegen`, sinon le typage du binding ment. Build scripts autorisés via `pnpm-workspace.yaml` (`allowBuilds` : `esbuild`, `workerd`), pas le champ `pnpm` de package.json (ignoré en pnpm 11).
- SQLite n'a pas de type date : `slotStart`/`createdAt` sont des chaînes ISO UTC. Passer par `record.ts` (`slotKey`) plutôt que de sérialiser à la main dans une requête. La colonne `packages` de `Booking` est un reliquat de l'ancien panier : plus rien ne l'écrit ni ne la lit, son `DEFAULT '[]'` la remplit — aucune migration nécessaire.
- **Le verre dépoli a été retiré** avec la charte A3 : fonds opaques dérivés du thème pour l'en-tête, le menu et la modale. Disparaissent avec lui trois pièges — l'ordre des préfixes `backdrop-filter` que lightningcss fusionnait en supprimant la propriété standard, le `@supports not` de repli pour un Chrome sans accélération matérielle, et la réfraction `url(#svg)` Chromium-only. Ne pas les réintroduire sans relire cette ligne.
- **Un carrousel se mesure en unités de conteneur.** `.carousel { container-type: inline-size }` et les diapositives en `cqw` : un pourcentage se rapporterait à la boîte de contenu du défileur, donc à sa largeur **moins son padding** — lequel dépend lui-même de la largeur d'une diapositive. La circularité produit des diapositives qui rétrécissent à chaque recalcul.
- **Un en-tête `sticky` dans un conteneur qui défile** doit déborder jusqu'aux bords de ce conteneur (marges négatives + `top` négatif égal au padding), sinon le contenu réapparaît dans la marge au-dessus de lui. Cas réel : le titre de la modale de rendez-vous.
- **Une illustration dont la mise en page dépend de sa boîte, pas de l'écran** : le planning de « Construire » passe en téléphone seul via `@container`, ce qui couvre d'un coup le mobile et la colonne étroite du hero des pages dédiées. Avec des media queries, la même règle était écrite deux fois et le téléphone se faisait rogner entre 700 et 1165px.

## Workflow

- **`CLAUDE.md` est un lien symbolique vers `AGENTS.md`, et pas l'inverse.** C'étaient deux copies identiques de 99,7 Ko : toute édition de l'une divergeait de l'autre en silence. Le sens compte : `CLAUDE.md` est **ignoré par le gitignore global** de la machine (`~/.gitignore_global`) et n'est donc pas versionné — c'est `AGENTS.md` qui est suivi par git et qui part dans le dépôt public. Faire pointer `AGENTS.md` vers `CLAUDE.md` livrerait un **lien mort** à quiconque clone. `next dev` continue de fonctionner : `writeAgentFiles` écrit par `writeFileSync` sur `AGENTS.md`, qui est le fichier réel. Ne pas « réparer » le lien en recréant un fichier.
- **La CI a trois travaux** (`.github/workflows/ci.yml`) : `verify` (lint, test, build), `e2e` (Playwright, chromium installé à la demande, rapport téléversé en cas d'échec) et `smoke` (ce que workerd sert vraiment). Les actions tierces sont **épinglées par SHA**, pas par tag. Les 48 tests Playwright ne protégeaient que la machine du développeur avant d'entrer en CI.
- Ne jamais committer sans demande explicite de l'utilisateur.
- Vérification avant livraison : `pnpm lint && pnpm test && pnpm build`, puis contrôle visuel navigateur (mobile 375px + desktop, light + dark, reduced-motion).
- Trois contrôles que l'œil ne fait pas et qui ont chacun rattrapé un bug réel :
  - `document.documentElement.scrollWidth === clientWidth` à 320, 390, 768, 1440 et 1920 px, sur les quatre pages statiques. Un dépassement fait dézoomer toute la page sur mobile, sans autre symptôme.
  - après un scroll complet **et 2 s de repos** (les reveals durent 0,7 s plus leur délai), aucun `[data-reveal]` visible ne doit rester sans `data-in`. Mesurer l'opacité trop tôt donne un faux positif massif.
  - contraste : les tokens sont en `lab()`/`oklch()` et les fonds sont souvent semi-transparents. Un calcul naïf via `getComputedStyle` renvoie n'importe quoi — il faut **composer l'alpha** sur le fond opaque parent avant de comparer.
- Lighthouse sur une machine chargée est ininterprétable : le TBT mobile a varié de 122 à 1 033 ms selon la charge. Toujours mesurer à `load average` bas et prendre la **médiane de 3 passes**.
