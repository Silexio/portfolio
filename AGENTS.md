# Portfolio Silexio

Site bilingue (FR défaut + EN) de Silexio, studio d'ingénierie indépendant — silexio.be. Une landing one-page (`/fr`, `/en`) et trois pages dédiées à slug localisé (`/fr/automatisation`, `/fr/logiciel-metier`, `/fr/depannage` et leurs équivalents anglais), toutes 100% statiques (SSG). La réservation (cf. § Réservation) et le formulaire de demande (cf. § Formulaire) introduisent le seul code serveur dynamique du projet (Route Handlers serverless) — les pages restent SSG.

## Commandes

```bash
pnpm dev              # dev server (les bindings wrangler sont injectés par initOpenNextCloudflareForDev)
pnpm build            # build prod — /fr, /en, /[lang]/legal et les 6 pages dédiées doivent rester ● (SSG) ; /api/* et /[lang]/booking/[action] sont ƒ (dynamiques, attendus)
pnpm lint             # eslint, zéro warning toléré
pnpm test             # vitest — lib/**/*.test.ts uniquement (unit)
pnpm test:e2e         # playwright — e2e/*.spec.ts (chromium + mobile iPhone 13), démarre le dev server. `npx playwright install` une fois.
pnpm preview          # build OpenNext + exécution locale dans workerd — le vrai runtime de prod
pnpm deploy           # build OpenNext + déploiement Cloudflare
pnpm db:migrate       # applique migrations/ à la D1 locale (.wrangler/state)
pnpm db:migrate:remote# idem sur la D1 de prod
pnpm cf-typegen       # régénère cloudflare-env.d.ts (auto en postinstall) — relancer après toute modif de wrangler.jsonc
```

`pnpm start` n'existe plus : la prod tourne sur workerd, pas sur le serveur Node de Next. Pour tester le comportement réel, c'est `pnpm preview`.

## Architecture

- `app/[lang]/` — seul segment de routes. `generateStaticParams` + `dynamicParams = false`, y compris sur `app/[lang]/[service]` (pages dédiées), dont le `generateStaticParams` reçoit la langue du parent de façon **synchrone** (`{ params: { lang } }`). Les params de page Next 16 sont des Promises : toujours `localeParam(params)` (lib/i18n/utils.ts), jamais de cast.
- `/` → redirect 308 vers `/fr` (next.config.ts), `x-default` hreflang pointe sur `/fr`.
- `lib/data.ts` — TOUT le contenu UI vit ici en `Bilingual { fr, en }`. Jamais de string utilisateur en dur dans un composant.
- **Positionnement** (refonte du 2026-09-21, spec : `docs/superpowers/specs/2026-09-21-repositionnement-silexio-design.md`) : le site vend un **résultat** (« la tâche que vous refaites chaque semaine peut disparaître »), pas une compétence technique. Cible : PME wallonnes de 5 à 50 personnes. Le dépannage IT des particuliers est **sorti de la landing** vers `/[lang]/depannage` : il rapporte vite mais tirait la marque vers « informaticien local ». Toute réécriture de contenu doit tenir cette ligne.
- **Cas client** (`CaseStudy.tsx`) : `CASE_STUDY` met en avant le projet `projectId` de `PROJECTS` (SCALENEO) — problème, solution, faits vérifiés (`facts`, tirés de l'outil et de son README) et un bloc « Temps gagné » calculé par `lib/roi.ts`. `roi` reste à `null` tant que le client n'a pas fourni ses trois chiffres (minutes avant, minutes après, rapports par semaine) : le bloc est alors **masqué**, jamais estimé. L'énoncé du problème est reconstruit à partir des fonctions de l'outil — à faire valider par le client.
- **Pour les curieux** (`Curious.tsx`) : les autres `PROJECTS` en cartes compactes (chips statut + `kind` client/personnel, boutons `site` / `install` / `repo`, un champ vide masquant son bouton), puis `STACK_GROUPS` et **un seul bouton « Voir mon GitHub »** vers l'organisation Silexio. Placé après la preuve et les tarifs : un patron de PME n'a pas à traverser une liste de dépôts. Le carrousel APG qui présentait les projets a été **retiré** avec la refonte (un îlot client de moins) ; le fetch des étoiles GitHub l'avait été avant : aucun appel réseau au build.
- **Avis** : `REVIEWS` (Google, Trustpilot) est relevé **à la main** — `checkedOn` date le relevé. Ni Google ni Trustpilot ne sont relevables par script (captcha côté Google, 403 côté Trustpilot) : le chiffre vient de l'exploitant de la fiche. En dessous de `MIN_REVIEWS`, la plateforme reste masquée : « 1 avis » dessert plus qu'il ne prouve. Ces notes ne vont **jamais** dans le JSON-LD : Google refuse le markup `aggregateRating` bâti sur des avis collectés ailleurs.
- **Marque Silexio** : `components/ui/Mark.tsx` — vecteur **inline**, pas une image. Le tracé (16 facettes, extrait de `public/icon.svg`) n'est écrit qu'une fois dans `<MarkSprite />`, rendu par le layout ; les usages (hero, nav, footer) sont des `<use href="#silexio-mark">`. Deux raisons, mesurées : un `<img>` décoratif de 234 px était le **plus grand élément peint du hero, donc l'élément LCP**, pour une texture à 7 % d'opacité — les `<path>` SVG, eux, ne sont pas candidats au LCP ; et un tracé dupliqué serait inliné deux fois par usage dans le document (Next y embarque aussi la charge RSC). Les sélecteurs CSS ciblent `svg`, pas `img`.
- Icônes : `app/favicon.ico` doit rester en **16/32/48** (~4 Ko). Il contenait 6 tailles jusqu'à 256×256 non compressées, soit **110 Ko chargés en priorité `High`** dans la fenêtre critique — plus lourd que n'importe quelle police. `icon.png` en 192 px et `apple-icon.png` en 180 px suffisent : le manifeste porte son propre jeu `public/icon_x*.png` pour la PWA.
- `images: { unoptimized: true }` (next.config.ts) : sur Workers, `/_next/image` dépend de Cloudflare Images, non provisionné — il renvoyait l'original en payant une requête Worker de plus. Les visuels sont donc pré-dimensionnés en WebP. Toute image ajoutée doit l'être aussi.
- **Offres et tarifs** : `OFFERS` (`lib/data.ts`) est l'échelle que gravit un client — premier échange (gratuit), diagnostic (490 € HTVA), sprint automatisation (dès 1 500 €), outil métier (dès 4 500 €), suivi (dès 150 €/mois). C'est **le seul endroit où vivent les prix** : `OfferLadder` les affiche via `priceParts` (`lib/price.ts`, pur et testé), le JSON-LD en dérive, la FAQ y renvoie sans les recopier. Ce sont des prix de lancement, à réviser dès que les premiers chiffres de conversion sont connus. Le premier échange occupe toute la largeur de l'échelle ; au-delà de 1100px, une colonne par offre payante via `--paid` (posé par `OfferLadder`) — `auto-fit` ne peut rien replier puisque le bandeau occupe toutes les pistes.
- **Solutions** (`Solutions.tsx`) : `DOMAINS` = Automatiser / Connecter / Construire, chacun avec des exemples concrets et un lien vers sa page dédiée, puis un renvoi discret vers le dépannage. L'ancien panier de packages (`usePackages`, `PackageCard`, `ContactActions`) a été **supprimé** : avec trois familles et une échelle de prix, c'est le formulaire qui qualifie le besoin, pas une sélection.
- **Footer** (`Footer.tsx`) : quatre colonnes — marque + tagline + localité, Services (les trois pages dédiées), Contact, Suivre — puis une **barre basse** fine portant copyright, entité Smart et TVA. `base` préfixe l'ancre de la marque (`/{lang}#top` hors accueil). Les mentions légales belges obligatoires (entité, siège de facturation Smart, BCE/TVA, lien mentions légales) doivent rester dans ce footer unique.
- Réseaux sociaux : `lib/data.ts` `SOCIALS` (LinkedIn, GitHub, Facebook, Instagram, Threads) + `SocialIcon` (glyphes de marque) dans le footer. URLs Facebook/Instagram/Threads = handle `silexio` supposé, à confirmer. **WhatsApp n'est pas dans `SOCIALS`** : c'est un CTA de contact, pas un profil à suivre. Il vit dans la même rangée mais en pilule libellée (`.footer__social--cta`, glyphe + texte), alimenté par `LEGAL.whatsappUrl`. Son `id` existe dans `SocialId` uniquement pour que `SocialIcon` connaisse le glyphe.
- `t(node, lang)` se résout **côté serveur uniquement** — les composants client reçoivent des strings déjà résolues (aucun dictionnaire dans le bundle client).
- Composants : `components/sections/` (un par section, plus `ServiceDetail` pour le corps des pages dédiées et `LeadForm`), `components/layout/` (Nav, ChapterMarkers, Footer), `components/ui/` (primitives, dont `BookingButton` — le seul îlot client nécessaire pour poser un CTA d'appel dans un composant serveur — et `OfferLadder`). PascalCase. Pattern Nav.tsx (serveur, résout les labels) → NavClient.tsx (client).
- Ordre des sections (`page.tsx`) et numérotation `SectionHead` : Hero, Solutions `01`, CaseStudy `02`, Offers `03`, About, Proof, Curious, Faq `04`, Contact. Le `num` de `SectionHead` est facultatif : Hero, About, Proof, Curious et Contact n'en portent pas, c'est la porte de sortie pour ajouter une section sans renuméroter la suite (les `num` sont en dur à l'appel).
- **Longueur de la page** : c'est le reproche récurrent sur une landing. Mesuré après la refonte (1440×900, `prefers-reduced-motion`) : **12 écrans** (13,8 avant, dont 3,3 pour l'ancien scrollytelling Process, supprimé), 14,2 à 390px. Avant d'ajouter une section, mesurer : `document.documentElement.scrollHeight / window.innerHeight`.
- `About.tsx` (`ABOUT` dans data.ts) : `photo` vide masque le portrait et repasse la grille sur une colonne (`about__grid--portrait`). Ne jamais y mettre un visage d'illustration — un faux portrait détruit exactement la confiance qu'un vrai installe. Le texte ne doit affirmer que des faits prouvables : pas d'ancienneté ni de nombre de clients inventés.
- **Pages légales** : `app/[lang]/legal/page.tsx` (SSG, 2 locales), contenu dans `lib/legal.ts` — hors de `lib/data.ts` pour ne pas noyer le contenu marketing sous le juridique, même exception que `lib/i18n/error-page.ts` et `lib/services.ts`. La page décrit les traitements **réellement** effectués par le code : toute évolution du booking, du formulaire de demande, du mailer ou de l'observabilité doit y être répercutée. `Nav` accepte `base` (préfixe des ancres) et `altPath` (équivalent dans l'autre langue) — sans eux, les liens de section d'une page hors accueil ne mènent nulle part.
- Les `<section>` internes d'une page héritent de la règle globale `section { padding-block: var(--section-y) }` : les neutraliser (`padding-block: 0`) quand ce sont des sous-parties et non des sections de page.
- `Proof.tsx` est une **bande d'avis**, pas une section titrée, et rend `null` tant que `REVIEWS` (au-dessus de `MIN_REVIEWS`) et `TESTIMONIALS` sont vides. Les engagements chiffrés maison (délai de réponse, devis gratuit, code livré) en ont été **retirés volontairement** : une promesse qu'on se donne à soi-même n'est pas une preuve, et affichée sous un titre « Confiance » elle se lit comme un argument de vente. Seul ce qui est vérifiable chez un tiers reste. Ces engagements restent dits ailleurs — en prose dans la FAQ et About.
- **Zone d'intervention** : pas de section sur la landing. `COVERAGE` (`lib/data.ts`) alimente les entrées `areaServed` du JSON-LD et la zone d'intervention affichée sur `/[lang]/depannage`, la seule page où elle aide à décider. La question « Dans quelles communes vous déplacez-vous ? » a donc quitté les FAQ : la liste visible y répond.
- **Pages dédiées** (`app/[lang]/[service]/page.tsx` + `ServiceDetail`) : contenu dans `lib/services.ts` (`SERVICE_PAGES`), slug **par langue** (`automatisation`/`automation`, `logiciel-metier`/`custom-software`, `depannage`/`it-support`), helpers purs `servicePage`, `findServicePage`, `servicePath`, `serviceSlugs` (testés, dont l'unicité des slugs et le fait qu'aucun ne masque `legal` ni `booking`). Gabarit : hero (H1 + CTA formulaire + CTA appel), situations, démarche, offres concernées **ou** zone d'intervention (dépannage), FAQ propre, formulaire. Chaque page émet son `Service` et **sa** `FAQPage` en JSON-LD, jamais celle d'une autre. Métadonnées : `openGraph()` de `lib/metadata.ts` — Next fusionne les métadonnées clé par clé sans descendre dans les objets, une page qui redéfinit `openGraph` doit donc le fournir en entier.

## Réservation (booking) — seul code serveur dynamique

Système natif qui a remplacé Cal.com (moins de dépendance tierce). **Pas de section dédiée** : le RDV s'ouvre dans une **modale `<dialog>` glass** depuis les CTA « Réserver un appel » (Contact + menu mobile).

- **Flux** : `Booking.tsx` (serveur, résout les labels) monte `BookingModal.tsx` (client, `<dialog>` natif) **une seule fois** après le Footer, sur l'accueil comme sur chaque page dédiée. Les CTA appellent `openBooking()` (store `useBookingModal`, `useSyncExternalStore` sans Provider) — depuis un composant serveur, via `BookingButton` (hero, contact, pages dédiées) ; `Btn` accepte `href` **ou** `onClick`. La modale contient `BookingClient.tsx` → calendrier Lun-Ven 8h-16h **Europe/Brussels**, créneaux 30 min, fenêtre 3 semaines (config `BOOKING`). Le `GET /api/availability` n'est appelé **que quand la modale est ouverte** (prop `active`), jamais au chargement de page. Le visiteur choisit un créneau, remplit nom/email/téléphone/visio|appel + Turnstile → `POST /api/bookings`. Le propriétaire reçoit un email avec liens signés **Confirmer/Refuser** → page **2-temps** `/[lang]/booking/[action]` (GET affiche un bouton → POST exécute, anti-prefetch) → `/api/bookings/{confirm,refuse}`. La confirmation génère le lien kMeet (`kmeet.infomaniak.com` — instance Jitsi d'Infomaniak, room anonyme créée à la première connexion : lien unique, tout le monde est modérateur. L'API `POST /1/kmeet/rooms` existe mais n'est **pas** utilisée : elle imposerait un token, un scope `kmeet` et un appel réseau faillible dans le flux de confirmation) et envoie un email **au client ET au propriétaire**, chacun avec une **pièce jointe `.ics`** (`lib/booking/ics.ts`, VEVENT RFC 5545, ajoutable dans tout agenda) portant le lien visio en lieu.
- **Chargement différé** : `BookingModal` importe `BookingClient` via `next/dynamic` et ne le rend que si `session > 0`. Calendrier, formulaire et Turnstile ne sont donc montés qu'au premier clic sur « Réserver un appel », pas à chaque visite. `session` ne redescend jamais : une fois montée, la modale le reste, y compris pendant sa transition de fermeture. Mesuré sur réseau lent : modale ouverte en 316 ms avec titre et état de chargement, calendrier à 1,1 s — pas de flash vide.
- **Modale** : `<dialog>` natif (`showModal()` → focus-trap, Esc, top-layer gratuits), glass cohérent avec `.sheet`, animée via `@starting-style` + `transition-behavior: allow-discrete` (`opacity`/`transform`/`overlay`/`display`). Clic backdrop (`target === dialog`) ou `close` event → `closeBooking()`. `body { overflow: hidden }` quand ouverte.
- **Synchronisation agenda (lecture seule)** : `GET /api/availability` croise **deux sources** — les demandes déjà reçues (table D1) et les agendas publiés par le studio. `BOOKING_CALENDAR_ICS_URL` contient une ou plusieurs URLs iCalendar séparées par des virgules (kCalendar Infomaniak : _Partager publiquement un agenda_ → URL de la forme `https://sync.infomaniak.com/calendars/<compte>/<uuid>?export`, qui répond en `text/calendar` sur un simple GET sans authentification). `calendar.ts` les récupère (timeout 4 s, plafond 2 Mo, **cache mémoire de 2 min** — sans lui chaque ouverture de modale paie un aller-retour vers l'agenda, ~100 ms mesurés, et le service tiers encaisse une requête par visiteur), `ical.ts` les analyse. **Pas de CalDAV, pas d'OAuth, pas de token à renouveler** : un simple GET, ce qui passe sans friction sur workerd.
  - **Accès authentifié à privilégier.** Le serveur est un SabreDAV : l'URL `?export` répond **200 sans aucune authentification** (quiconque la détient lit l'agenda), tandis que la collection CalDAV répond `401 WWW-Authenticate: Basic realm="sabre/dav"`. Renseigner `BOOKING_CALENDAR_AUTH` (`identifiant:mot-de-passe-application`) permet donc de **révoquer le partage public** et de lire l'agenda par Basic Auth. Chez Infomaniak, générer un _mot de passe d'application_ dédié — révocable seul, et obligatoire dès que la 2FA est active. Sans cette variable, le comportement reste celui d'une URL publique.
  - L'agenda branché est l'agenda **principal du studio** (« Nicolas Wieckiewicz »), pas un agenda dédié : ce qui y figure fait foi pour la disponibilité, sans double saisie. L'URL est un secret Worker, mais elle expose le contenu de l'agenda publié — le compte kCalendar est strictement professionnel, le privé vit ailleurs.
  - Conséquences d'un agenda principal, à connaître avant de s'étonner : un événement **journée entière** bloque la journée complète (anniversaires, jours fériés importés) — le marquer « Disponible » dans kCalendar (`TRANSP:TRANSPARENT`) le neutralise. Une **invitation déclinée** qui reste dans l'agenda bloque encore : la supprimer. Un événement **provisoire** (`STATUS:TENTATIVE`) bloque volontairement — un « peut-être » ne se vend pas comme libre.
  - `ical.ts` est **pur et testé** (19 tests) : dépliage RFC 5545, `DTSTART`/`DTEND`/`DURATION`, `TZID` et journées entières, `RRULE` (DAILY/WEEKLY/MONTHLY/YEARLY avec INTERVAL, COUNT, UNTIL, BYDAY), `EXDATE`, et exclusion de `STATUS:CANCELLED` et `TRANSP:TRANSPARENT`. Les formes rares (BYSETPOS, BYMONTHDAY multiples) ne sont pas dépliées — l'occurrence de base reste bloquée, jamais l'inverse.
  - **Dégradation volontairement ouverte** : agenda injoignable, lent ou illisible → aucune plage remontée, tous les créneaux restent réservables. Fermer bloquerait toute prise de rendez-vous sur une panne tierce, alors que le pire cas ici est une demande à refuser — ce que le flux de confirmation permet déjà. Ne pas inverser ce choix sans mesurer ce qu'on perd.
  - La synchro est **unidirectionnelle**. Le `.ics` envoyé à la confirmation va dans l'autre sens (réservation → agenda) : rien n'écrit dans kCalendar.
- **Logique pure testable** dans `lib/booking/*.ts` (`slots`, `schema` Zod, `token` HMAC, `meeting`, `email`, `format`, `ics`, `record`) — couverte par vitest, **sans réseau ni DB**. Effets de bord non testés : `db.ts`, `mailer.ts`, `turnstile.ts`, `actions.ts`. Toute nouvelle logique métier va dans `lib/booking/` pour rester testable — c'est pour ça que le mapping ligne SQL → domaine vit dans `record.ts` (pur) et pas dans `db.ts`.
- **Runtime** : Cloudflare Workers (workerd) via OpenNext. Aucun `export const runtime` : le flag `nodejs_compat` couvre tout ce que le code utilise (`node:crypto` complet depuis avril 2025, `node:buffer`, et `process.env` peuplé automatiquement avec les vars + secrets). `GET /api/availability` + la page action déclarent `dynamic = "force-dynamic"`.
- **DB** : Cloudflare **D1** (SQLite), binding `DB` déclaré dans `wrangler.jsonc`, typé par `cloudflare-env.d.ts` (généré par `wrangler types`, gitignored, régénéré en `postinstall` — ne jamais l'écrire à la main). Accès via `getCloudflareContext({ async: true })` dans `lib/booking/db.ts`. La DDL vit dans `migrations/` et s'applique avec `wrangler d1 migrations apply`, jamais à la main dans le dashboard. **Pas d'ORM** : 2 tables, ~6 requêtes préparées.
- **Dates en SQLite** : pas de type date. Tout est stocké en **ISO 8601 UTC** (`2026-01-14T07:00:00.000Z`), ce qui trie et compare lexicographiquement — d'où le `BETWEEN` sur `slotStart`. Toujours passer par `slotKey()` (`record.ts`) avant d'écrire : deux écritures du même instant dans deux formats différents contourneraient l'index unique.
- **Anti-double-booking** : index UNIQUE **partiel** `Booking(slotStart) WHERE status IN ('pending','confirmed')` (`migrations/0001_create_booking.sql`). Insert + catch `UNIQUE constraint failed` → `insertBooking` renvoie `null` → 409. Jamais de check-puis-insert. Un refus libère le créneau.
- **Transitions de statut** : `settleBooking` fait `UPDATE ... WHERE id = ? AND status = 'pending'` et lit `meta.changes` — l'idempotence est garantie par la DB, pas par un read-then-write qui perdrait la course en cas de double clic.
- **Anti-abus** : Cloudflare Turnstile (vérif serveur `turnstile.ts`, hors CSP navigateur) + rate limit D1 par IP **hashée HMAC** (table `RateLimitHit`, RGPD : jamais d'IP en clair ; `clientIp` lit `cf-connecting-ip` en priorité, non spoofable derrière Cloudflare) + honeypot champ `company`. Le formulaire de demande réutilise les trois (même table `RateLimitHit`, donc un quota horaire commun aux deux formulaires).
- **Emails** : API HTTP **Brevo** (`POST /v3/smtp/email`, `mailer.ts`) — Workers ne peut pas ouvrir de socket SMTP. Expéditeur = un sender vérifié Brevo (`BREVO_SENDER_EMAIL`), `replyTo` sur `EMAIL` sauf si le `Mail` en fournit un (`replyTo`, utilisé par la notification du formulaire de demande pour répondre directement au prospect). Les `.ics` partent en pièce jointe base64.
- **Liens d'action** : HMAC `BOOKING_ACTION_SECRET` (`token.ts`, comparaison `timingSafeEqual`). Routes `confirm`/`refuse` = un seul helper `runBookingAction` (`actions.ts`). Idempotent, refusé si créneau passé.
- **Formulaire de demande** (« Montrez-moi la tâche », « Décrivez la panne ») : `LeadForm.tsx` (client) → `POST /api/leads` → notification au propriétaire (`BOOKING_NOTIFY_EMAIL`, à défaut `EMAIL`, en français, `replyTo` = prospect) + accusé de réception au prospect. Champs : tâche (20–2000 car.), temps perdu par semaine (facultatif, masqué sur le dépannage), email, `source` (`home` ou l'id de la page dédiée — mesure quelle page convertit). **Rien n'est stocké** : l'email est la seule trace, donc un échec de la notification renvoie 502 et le prospect voit l'erreur avec l'adresse de contact ; l'accusé de réception reste best-effort et **ne reprend jamais le texte saisi** (sinon le formulaire relaierait n'importe quel contenu vers n'importe quelle adresse). Turnstile n'est monté qu'au **premier focus** dans le formulaire : aucun script tiers au chargement de page. Un jeton Turnstile ne sert qu'une fois : après un échec, le widget est remonté (`attempt`). Logique pure dans `lib/leads/` (`constants` sans zod, importable côté client ; `schema` ; `email`), testée.
- **Setup (une fois)** : `pnpm db:migrate` (local) et `pnpm db:migrate:remote` (prod), puis l'env — voir `.env.example` (`NEXT_PUBLIC_TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY`, `BREVO_API_KEY`, `BREVO_SENDER_EMAIL`, `BOOKING_NOTIFY_EMAIL`, `BOOKING_ACTION_SECRET`, `IP_HASH_SECRET`, `BOOKING_CALENDAR_ICS_URL` — cette dernière facultative : sans elle la synchro agenda est simplement inactive). En prod ce sont des secrets Workers (`wrangler secret put`), pas des `vars`. Clés de test Turnstile fournies pour le dev.
- **Contenu** (`lib/data.ts`) : `I18N.booking` (UI, résolu en bloc via `resolveDict` → type `BookingLabels`), `BOOKING_EMAILS` (templates FR/EN, placeholders `{...}` + échappement HTML dans `email.ts`), `BOOKING_ACTION` (page action). Pas de chapitre `booking` dans `CHAPTERS` (c'est une action, pas une section). Pages action en `noindex` + disallow robots.

## CSS — décision structurante

`app/globals.css` est un design system BEM écrit à la main (tokens OKLCH, light/dark via `[data-theme]`), porté tel quel depuis le prototype design. **Ne pas réécrire en utilities Tailwind.** Tailwind 4 sert le preflight + utilities ponctuelles via le bloc `@theme inline` (couleurs `bg/fg/accent`, fonts).

- Tokens en haut du fichier ; le thème sombre redéfinit les mêmes variables sous `[data-theme="dark"]`. Radius : `--radius-pill` / `--radius-card`. Espacement : `--pad-card` / `--gap-card` / `--gap-chips` (échelle harmonisée — les paddings/gaps de cartes étaient divergents par section, volontairement unifiés ; ne pas les redécliner par section).
- Primitives partagées (sélecteurs groupés, zéro duplication) : **grille mosaïque** (`.domains`/`.stack__grid`/`.case__facts`/`.situations` : filet de 1px peint par le fond de la grille, coins clippés ; chacune ne redéfinit que ses colonnes), **surface et layout de carte** (`.domain` + `.stack__group`), **micro-libellé** (`.case__numbers-title`/`.curious__stack-title`/`.coverage__label`), **numéro d'étape** (`.offer__step`/`.step__num`), liens accent soulignés, champs de formulaire communs au booking et à la demande (`.booking-form__field`/`.lead-form__field`), pastille live pulsante (`.chip--live`/`.status-pill__dot`), wordmark mono (nav + footer), filtres dark des logos. Reveals = deux keyframes seulement, `line-rise` (hero, par ligne) et `hero-reveal` (tout le reste, décalé par `--d`) — cf. Animations.
- **Échelle typographique** : H1 du hero `clamp(38px, 5.6vw, 76px)`, titres de section (`.section-head__title`, `.featured__title`) `clamp(30px, 4.4vw, 58px)`. Le H1 était à **148px** et les h2 à 88px — les sous-titres écrasaient le titre principal, et le mot le plus long touchait les deux bords. Un h2 ne doit jamais dépasser le h1 : si l'un des deux bouge, rebaser l'autre.
- **Hero** : `.hero__inner` porte `.wrap` (donc `margin: 0 auto`) **et** est un flex item de `.hero` (flex column). Sans `width: 100%` explicite il se réduit à son contenu et se recentre — le hero se désaligne alors de la grille du reste du site. Ce bug était masqué tant que le H1 faisait 148px : il débordait, donc l'item était clampé à `--content-max` par accident.
- **Cristal du hero** (`.hero__shard`) : c'est une **texture de marque, pas un sujet**. Largeur `clamp(320px, 38vw, 560px)`. Son opacité est pilotée par le token **`--shard-peak`** (0.13 desktop, **0.07 sous 760px** : sur mobile le texte occupe toute la largeur, le cristal passe forcément derrière et doit descendre sous le seuil de perception) ; les trois keyframes et la règle `prefers-reduced-motion` en dérivent par `calc()`, donc une seule valeur à changer. Attention, `shard-scroll` est **redéfini** dans un `@media (min-width: 760px)` : modifier la version de base ne suffit pas. Il faisait 85vw à 0.22 d'opacité : il dominait la page, chevauchait le pitch et donnait au hero un air de fond d'écran 3D. Ne pas le regrossir.
- **Marqueurs de chapitre** : sous 1500px la colonne mord sur la grille de contenu et le label chevauche le titre. Il est donc masqué **visuellement** (technique `.sr-only` inline, pas `display: none`) sous ce seuil : c'est le seul texte du lien, le retirer de l'arbre a11y lui ôterait son nom accessible.
- Contraste : `--accent` (L 54%) tient AA sur `paper`, **mais pas** sur `bg-alt` (4.46:1) ni sur `--accent-tint` (4.35:1). D'où **`--accent-ink`** (light L 50%, dark = `--accent`) : c'est le token à utiliser pour **tout texte accent posé sur un fond teinté ou alternatif** — `.chip--ember`, `.status-pill`, `.proof__review-cta`, `.case__label`, `.offer__step`/`.step__num`, les liens (`.domain__link`, `.contact__email`), les erreurs de formulaire (`.booking-form__error`/`.lead-form__error`, posées sur `bg-alt`), et les états actifs/hover (`.booking-cal__day`, `.booking-form__mode`, `.footer__social`). `--accent` reste pour les aplats CTA et les bordures. `--fg-subtle` (light 50% / dark 58%) tient AA sur paper et bg-alt. Ne rien éclaircir sans re-mesurer : la conversion OKLCH→sRGB se mesure via un canvas 2D (`getComputedStyle` renvoie l'OKLCH brut, pas du rgb).
- Les animations scroll-driven CSS (`.hero__shard`, `.scroll-progress`) sont gardées derrière `@supports (animation-timeline: scroll())` — sans ce guard, Firefox/Safari affichent l'état final figé (barre pleine largeur). Ne pas retirer.
- `prefers-reduced-motion` coupe tout (section 17) — préserver à chaque ajout d'animation.

## Animations

**Le projet n'a plus de bibliothèque d'animation.** Motion a été retiré (`pnpm remove motion`) : il pesait ~74 Ko transférés et une hydratation par instance sur 12 `<Reveal>`, pour un effet reproductible en CSS. Tout ce qui suit est du keyframe CSS ; le seul JS restant est un IntersectionObserver de huit lignes. Ne pas réintroduire de dépendance d'animation sans mesurer ce qu'elle coûte au LCP simulé (cf. § Plafond de performance).

- Reveals (below-the-fold) : `components/ui/Reveal.tsx` est un **composant serveur** qui n'émet qu'un `<div data-reveal>` + `--d` (délai). L'état masqué est en CSS (`[data-reveal-js] [data-reveal]`), le déclenchement vient de l'IntersectionObserver du **script inline du layout**, qui pose `data-in`. Rien n'est monté côté client.
- `data-reveal-js` est posé par ce même script inline : **sans JS, l'attribut n'existe pas et le contenu reste visible**. C'est une correction, pas un détail — Motion rendait `opacity:0` côté serveur, donc toute la page sous le hero était vide sans JS.
- L'observer utilise `threshold: 0.12` (l'`amount` de Motion) et `unobserve` après déclenchement. Vérifié : saut instantané en bas de page, arrivée sur ancre, flick de 5 sauts en 5 frames — 17/17 révélés à chaque fois.
- Hero (above-the-fold) : `HeroLines.tsx` (keyframe `line-rise`) et la classe `.hero-reveal` (keyframe `hero-reveal`, délai par `--d`) sont **server-rendered**. **Ne jamais remettre le hero derrière une animation gatée par l'hydratation** : `.hero__pitch` était l'élément LCP et restait à `opacity: 0` jusqu'au JS — LCP mesuré à 9,7 s sur mobile, dont 93 % de render delay.
- Le bandeau défilant de technos sous le hero (`MARQUEE`, `.marquee`) a été **retiré** : il s'adressait à des pairs alors que la page vise un patron de PME, et la Stack porte déjà ce contenu plus bas. Ne pas le réintroduire dans le hero.
- `Neurons.tsx` (canvas de la section Contact) est **gardé par IntersectionObserver** : la boucle rAF ne tourne que quand le canvas est à l'écran. Sans ça elle tournait pendant toute la visite pour une section située en bas de 14 écrans.
- Toute animation reste sous `prefers-reduced-motion` (§ CSS). Les blocs `[data-reveal]` y repassent à `opacity: 1` **avant** tout scroll : le contenu ne doit jamais dépendre d'un déclencheur quand l'utilisateur a demandé moins de mouvement.

## Thème

`data-theme` sur `<html>`, posé avant le paint par le script inline du layout (anti-FOUC), persisté dans `localStorage("silex_theme")`. Le toggle (NavClient) écrit le DOM directement dans `document.startViewTransition` — **pas de state React pour le thème** (évite hydration mismatch + flushSync). Icônes lune/soleil swappées en CSS via `[data-theme]`. `suppressHydrationWarning` sur `<html>` **et `<body>`** est requis (le `<body>` neutralise les attributs injectés par des extensions navigateur — ex. ColorZilla `cz-shortcut-listen` — qui sinon provoquent un hydration mismatch console).

- `generateMetadata` par locale : canonical `/{lang}`, `alternates.languages` fr/en/x-default, OG `fr_BE`/`en_US` + `og:locale:alternate`, Twitter dérivé de l'OG par Next, `/opengraph.png` 1200×630. Meta description ≤ 160 car. (contrainte seobility). Lighthouse SEO / a11y / best-practices = 100.

Règle de fond : **un terme n'entre dans le contenu visible que s'il est expliqué** (« Full-stack veut dire… », « installation de postes, réseau, sauvegardes… ») ; sinon il se lit comme du bourrage et Google le traite comme tel. Vérifier la densité sur la page rendue avant d'en rajouter.
- **Référencement local** : Hainaut. Les titres, le H1 et le contenu sont écrits pour un patron de PME, pas pour un pair — le jargon est relégué à « Pour les curieux », assumé comme bonus technique. Toute réécriture de `lib/data.ts` doit tenir cette ligne.
- **Profil service-area** : `GEO` (`lib/data.ts`) ancre l'activité sur Chapelle-lez-Herlaimont **sans rue**, `COVERAGE` liste les communes servies. `LEGAL` porte l'entité de facturation Smart (Productions Associées asbl, Rue Coenraets 72, 1060 Bruxelles, BCE 0896755397) : elle vit **uniquement** dans le footer au titre des mentions légales belges. - La TVA est celle de la coopérative, partagée par tous ses membres : elle reste hors du JSON-LD (pas de `vatID`), sinon Google confond l'entité Silexio avec des milliers d'autres. Idem `telephone` : le numéro est privé, seul `LEGAL.whatsappUrl` (lien d'invitation `wa.me/message/…`) est publié — **ne jamais écrire le numéro dans ce dépôt, il est public sur GitHub**.

- JSON-LD dans `lib/seo.ts`, en **deux fonctions volontairement séparées** :
  - `structuredData(lang)` — identité du site, injectée par le **layout** donc présente sur toutes les pages du segment : `Person` (+ `hasOccupation`, 36 entrées `knowsAbout`) + `ProfessionalService`/`LocalBusiness` (geo, serviceArea, areaServed, hasOfferCatalog dérivé de `OFFERS` avec `PriceSpecification` HTVA — `minPrice` pour un prix « dès », `UnitPriceSpecification` mensuelle pour le suivi —, horaires) + `WebSite`.

Ne pas « durcir » sans comprendre ça. `'unsafe-eval'` est ajouté **en dev uniquement** (`isDev` dans next.config.ts) pour le tooling de debug de React ; la prod reste stricte (React n'utilise jamais eval en prod). ## Observabilité (Bugsink self-hosted)

**Bugsink** sur `sentry.silexio.be` parle le protocole Sentry. Le partage est asymétrique et volontaire : le SDK officiel côté **serveur**, un reporter écrit à la main côté **navigateur**.

### Serveur — `@sentry/nextjs`

- `instrumentation.ts` (`register` + `onRequestError`, et un warn au boot listant les env vars manquantes) et `sentry.server.config.ts`. Pas de config edge : OpenNext exécute tout en runtime `nodejs`. Supporté sur Workers via OpenNext grâce à `nodejs_compat` + `compatibility_date` ≥ 2025-08-16 (qui apporte `https.request`, requis par le transport Sentry).
- `tracesSampleRate: 0` — Bugsink n'ingère **que** des erreurs, les traces seraient jetées à l'arrivée. `sendDefaultPii: false` : les payloads de réservation portent nom, email et téléphone de prospects (Bugsink recommande `true` pour du self-hosted, c'est un choix délibéré du projet, pas un oubli).
- Inerte sans `SENTRY_DSN`.

### Navigateur — reporter maison, pas le SDK

`lib/observability/report.ts` (pur, 17 tests) construit une enveloppe Sentry v7 ; `lib/observability/client.ts` porte les effets de bord (deux écouteurs globaux, `fetch` en `keepalive`) ; `instrumentation-client.ts` l'installe ; `app/global-error.tsx` l'appelle pour ce que `window.onerror` ne voit pas.

- **Pourquoi** : `@sentry/nextjs` pèse 247 Ko bruts / 74 Ko transférés, soit ~30 % du JS de la page. Mesuré : le retirer fait passer le mobile de **84 à 92** et le desktop de **99 à 100**. Le reporter fait ~1 Ko.
- **Gardé** : type, message, pile parsée (dialectes V8 et SpiderMonkey/JavaScriptCore), URL, user-agent, environnement, déduplication par `type|message|frame`, plafond de 8 envois par page (un plantage en boucle ne doit noyer ni Bugsink ni le réseau du visiteur).
- **Perdu, assumé** : breadcrumbs (console, clics, fetch), contexte de route automatique, et la résolution symbolique par debug id — **les piles arrivent minifiées**. C'est le prix des 8 points. Si un jour la symbolication devient nécessaire, la remettre coûtera ce score.
- Vérifié de bout en bout au navigateur avec un DSN factice : 3 erreurs dont un doublon → 2 enveloppes ; 30 erreurs distinctes → plafonné à 8 ; enveloppe en 3 lignes, `event_id` de 32 caractères hex.
- **Ne pas remplacer par un import différé du SDK** : essayé, le chunk se retrouve dupliqué — JS 234 → 340 Ko et TBT 122 → 610 ms. Pire que l'import statique.

### Relais same-origin

- `app/monitoring/route.ts` reçoit l'enveloppe brute (cap 1 Mo) et la POST vers Bugsink, endpoint résolu par `lib/observability/dsn.ts` (pur, testé). Il existe parce que `connect-src 'self'` interdit d'atteindre le host du DSN depuis le navigateur, et parce que le `tunnelRoute` de `@sentry/nextjs` pointe **en dur** sur `ingest.sentry.io` : il ne peut pas atteindre un Bugsink self-hosted. Avant cette correction, **aucune erreur navigateur ne remontait, sans le moindre symptôme**. Coût : une requête Worker par event.
- `global-error.tsx` remplace le layout racine, donc il rend son propre `html`/`body` et ne peut pas résoudre `t()` côté serveur : ses textes vivent dans `lib/i18n/error-page.ts` (4 paires) et non dans `lib/data.ts`, pour ne pas embarquer tout le dictionnaire dans le bundle client. Sa carte réutilise les styles de `.booking-action` via un sélecteur groupé (`.fallback`), pas une copie.
- Source maps : uploadées **seulement si `SENTRY_AUTH_TOKEN`** (+ `SENTRY_URL`/`SENTRY_ORG`/`SENTRY_PROJECT`) par `withSentryConfig`, qui reste en place dans `next.config.ts` pour le serveur. Côté navigateur elles ne servent plus à grand-chose depuis le retrait du SDK, faute de debug id transmis.

## Pièges connus

- Routes typées Next 16 : utiliser les types globaux générés `LayoutProps<"/[lang]">` / `PageProps<"/[lang]">`.
- `as const` sur un objet avec tuples fr/en casse l'inférence de `t()` — typer explicitement (ex. `OFFERS: Offer[]`, ou `satisfies Record<string, Bilingual>` comme `META`).
- Vitest résout l'alias `@/` via `vitest.config.ts` (resolve.alias), pas via tsconfig.
- **Aucune police n'est téléchargée au build** : les quatre familles sont auto-hébergées et sous-échantillonnées dans `app/fonts/` (voir son `README.md` pour la procédure de régénération). C'est ce qui rend le build possible sans réseau — ne pas revenir à `next/font/google`, qui téléchargeait au build **et** servait des polices variables d'axe 100-900 pour deux graisses utilisées (120 Ko au lieu de 60).
- **Scripts tiers montés après le chargement** : ne pas utiliser `next/script` pour le widget Turnstile. Il est monté dans la modale, longtemps après l'événement `load` ; React n'exécute jamais une balise `<script>` insérée lors d'un rendu **client** (il le dit en console : « Scripts inside React components are never executed when rendering on the client »). Ni `lazyOnload` ni `afterInteractive` n'injectaient quoi que ce soit — le bouton « Envoyer » restait désactivé pour toujours, **sans la moindre erreur**. `Turnstile.tsx` charge donc l'API lui-même (`document.createElement` + promesse singleton partagée).
- **Cache CSS de `next dev`** : après une édition de `app/globals.css` faite hors de l'éditeur (script, sed), Turbopack sert parfois l'ancienne feuille — les nouvelles règles semblent ignorées alors que le fichier est correct. Symptôme : `getComputedStyle` renvoie les anciennes valeurs. Remède : `rm -rf .next/dev` puis redémarrer. `pnpm build` n'est jamais affecté.
- Une capture n'a pas à suivre le thème du portfolio : Reelmark est servi par sa capture **sombre dans les deux thèmes**, sa version claire étant délavée (affiches quasi invisibles). Choisir la capture qui vend le projet, pas celle qui s'accorde au fond.
- **Capture à côté du texte** (`.case__shot`) : l'image est sortie du flux en `position: absolute; inset: 0` au-delà de 900px, c'est le texte qui fixe la hauteur de la carte. L'ancienne version en `height: 100%` imposait une chaîne de hauteurs complète jusqu'à la grille : un maillon manquant faisait retomber l'image sur son ratio naturel et laissait une bande vide — `object-fit: cover` s'appliquant quand même, le diagnostic était trompeur.
- **Une `line-height` serrée plus `overflow: hidden` rogne la police.** `.hero__title` impose `1.02` alors que la boîte naturelle de Montserrat fait **1.219 em** (`hhea.ascender - hhea.descender` sur `unitsPerEm`) : le masque des `.line-reveal` coupait 8 px d'accents et de jambages à 38 px, 15 px à 76 px. Corrigé par `overflow-clip-margin: 0.16em`, qui étend la zone de clip **sans toucher à la mise en page** — un padding, lui, aurait déplacé les lignes. Vérifier après tout changement de police ou d'interlignage, et le vérifier **en image** : `getBoundingClientRect` ignore `overflow-clip-margin`, donc un détecteur qui compare les boîtes signale un faux positif.
- **`.sr-only` doit avoir un bloc contenant.** Il est en `position: absolute` : sans ancêtre positionné, il remonte jusqu'au premier qu'il trouve. Un `.sr-only` de bouton placé dans le scroller du carrousel s'est ainsi retrouvé rattaché à un ancêtre **hors** du scroller, qui ne le clippait donc pas : `document.scrollWidth` valait 1288 px pour un viewport de 390, et le mobile dézoomait toute la page. `.btn`, `.nav__lang` et `.footer__social` portent `position: relative` pour cette seule raison. Tout nouvel hôte de `.sr-only` doit en faire autant — le contrôle se fait au runtime, pas à l'œil : lister les `.sr-only` dont l'`offsetParent` est `body`.
- **Un `aria-label` remplace le texte visible, il ne s'y ajoute pas.** Le sélecteur de langue affichait « FR · EN » sous un `aria-label="Passer en anglais"` : nom accessible sans « EN », donc lien inatteignable à la commande vocale (WCAG 2.5.3, niveau A). Lighthouse le signale via `label-content-name-mismatch`, un audit **de poids 0** — invisible derrière un score d'accessibilité à 100. Le libellé passe par un `.sr-only` qui **complète** le texte.
- **Ordre et spécificité en CSS** : une media query **n'ajoute aucune spécificité**. Un bloc `@media (min-width: 900px)` posé _avant_ la règle de base d'un sélecteur de même poids est écrasé par elle. Toujours placer les surcharges responsive **après** les règles de base du composant.
- Collapsibles (`.sheet`) : `inert={!open}` (React 19), pas `aria-hidden` — sinon violation axe aria-hidden-focus.
- Mobile sheet (`.sheet`) : `display:none` fermé → `display:flex` ouvert, transition via `@starting-style` + `transition-behavior: allow-discrete` (en `transform` seul, le `backdrop-filter` laissait la sheet visible en haut). Garde desktop `@media (min-width:761px) { .sheet { display:none } }`. Ne pas revenir au transform-seul.
- D1 : `cloudflare-env.d.ts` est généré (gitignored) — après toute modif de `wrangler.jsonc`, relancer `pnpm cf-typegen`, sinon le typage du binding ment. Build scripts autorisés via `pnpm-workspace.yaml` (`allowBuilds` : `esbuild`, `workerd`), pas le champ `pnpm` de package.json (ignoré en pnpm 11).
- SQLite n'a pas de type date : `slotStart`/`createdAt` sont des chaînes ISO UTC. Passer par `record.ts` (`slotKey`) plutôt que de sérialiser à la main dans une requête. La colonne `packages` de `Booking` est un reliquat de l'ancien panier : plus rien ne l'écrit ni ne la lit, son `DEFAULT '[]'` la remplit — aucune migration nécessaire.
- **Ordre des préfixes `backdrop-filter`** : `-webkit-backdrop-filter` doit être écrit **AVANT** la propriété standard. lightningcss (le transformeur CSS de Tailwind 4) fusionne la paire et ne garde que la **dernière** forme ; avec la standard en premier, il ne restait que le `-webkit-`, jugé inutile pour les targets modernes, donc **supprimé** — le CSS servi n'avait plus aucune déclaration `backdrop-filter` et tout le verre tombait à plat (constaté sur Chrome 151, qui n'expose plus `-webkit-backdrop-filter`). Vérifier après toute modif : `getComputedStyle(document.querySelector('.nav__bar')).backdropFilter` ne doit pas valoir `none`.
- Un `@supports not ((backdrop-filter: …) or (-webkit-backdrop-filter: …))` repasse nav/sheet/modale sur un fond quasi opaque : sans lui, un Chrome sans accélération matérielle affiche du texte sur un voile translucide illisible.
- Liquid glass (`.nav__bar` + `.sheet`) : transparence (`color-mix` bg) + `backdrop-filter` blur/saturate (avec `-webkit-`) + lumière spéculaire (`::before`). 100% CSS portable, rendu identique Chrome/Safari/Firefox. La déformation par réfraction (`backdrop-filter: url(#svg)`) a été **retirée volontairement** : Chromium-only et fragile selon GPU/version (bug visuel observé sur certains Chrome, ignoré par Safari). Ne pas la réintroduire — pas de moyen CSS portable de réfracter le backdrop.

## Workflow

- Ne jamais committer sans demande explicite de l'utilisateur.
- Vérification avant livraison : `pnpm lint && pnpm test && pnpm build`, puis contrôle visuel navigateur (mobile 375px + desktop, light + dark, reduced-motion).
- Trois contrôles que l'œil ne fait pas et qui ont chacun rattrapé un bug réel :
  - `document.documentElement.scrollWidth === clientWidth` à 320, 390, 768, 1440 et 1920 px, sur les quatre pages statiques. Un dépassement fait dézoomer toute la page sur mobile, sans autre symptôme.
  - après un scroll complet **et 2 s de repos** (les reveals durent 0,7 s plus leur délai), aucun `[data-reveal]` visible ne doit rester sans `data-in`. Mesurer l'opacité trop tôt donne un faux positif massif.
  - contraste : les tokens sont en `lab()`/`oklch()` et les fonds sont souvent semi-transparents. Un calcul naïf via `getComputedStyle` renvoie n'importe quoi — il faut **composer l'alpha** sur le fond opaque parent avant de comparer.
- Lighthouse sur une machine chargée est ininterprétable : le TBT mobile a varié de 122 à 1 033 ms selon la charge. Toujours mesurer à `load average` bas et prendre la **médiane de 3 passes**.
